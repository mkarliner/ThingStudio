# Thingstudio — Design Document

**A drag-and-drop, low-code environment for programming microcontrollers**

Status: draft v0.1 · 2026-08-09

## 1. Vision

Thingstudio is a browser-based, node-and-wire visual programming environment, in the spirit of Node-RED, whose output runs directly on a microcontroller rather than on a server. A user drags nodes onto a canvas — sensors, GPIO, timers, logic, math, network — wires them together, and pushes the resulting flow to a physically connected or networked device. The device then runs the flow autonomously, with no host machine required afterward.

The core bet that differentiates Thingstudio from most prior art: flows are interpreted live by a small on-device virtual machine rather than compiled to native firmware. This trades a small amount of runtime performance for the thing that makes Node-RED itself so productive — editing a running system without a flash-and-reboot cycle, seeing live values on the wires, and swapping a flow in under a second.

## 2. Prior art and positioning

Several projects already occupy pieces of this space. Understanding what they do well — and where they fall short of "Node-RED for MCUs" — shapes the design choices below.

**Node-RED MCU Edition** (phoddie/node-red-mcu) is the closest existing analog. It runs actual Node-RED flows on microcontrollers by compiling them against the Moddable XS JavaScript engine, targeting ESP32 and a handful of other chips. It proves the concept is viable, but it works by cross-compiling a flow into a firmware image ahead of time — closer to "compile Node-RED to firmware" than a live, always-running on-device interpreter. There is no live-editing loop once a device is deployed; the workflow is still edit-compile-flash. It also validates that a general-purpose language VM (there, Moddable's XS engine for JS) is a workable foundation for this kind of tool; Thingstudio makes the same bet with MicroPython instead, for its broader board support and existing driver/sensor ecosystem (see §5, §7).

**MicroBlocks** is the strongest existing example of the live-interpreter model this project wants to follow. It is a Scratch-style block language with its own on-device bytecode VM, runs on ESP32, RP2040/Pico, micro:bit, and others, supports up to ten concurrent scripts, and lets you click a block in the browser and watch it execute on the board immediately. Its limitation for this project's purposes is the programming model: Scratch-style stacked blocks are excellent for sequential/event logic but don't represent dataflow (wires carrying live values between nodes) as directly as a Node-RED-style graph does.

**XOD** is a node-based dataflow language for Arduino/microcontrollers, closer to Thingstudio's visual metaphor (nodes and wires, not stacked blocks), but it generates native C++ and flashes a full firmware image per change — no live device interaction, no runtime flow updates.

**MicroFlo** is the one existing project that already combined exactly this trio — a node/wire dataflow editor (via Flowhub, the NoFlo-based FBP visual tool), a runtime that executes standalone on the microcontroller, and live introspection/reconfiguration without reflashing. It's a decade-old proof that the idea works: real deployments (a fridge thermostat, an LED installation) ran unattended for years starting in 2013. It's also a cautionary tale rather than a solved problem — its own README rates its status as "minimally useful," board support tops out at ESP8266 and pre-2015 Cortex-M0–M4/AVR8 parts (nothing in the ESP32 family), it's written in C++03 without exceptions or the standard library, and by every visible signal (220 stars, no sign of recent activity) it's dormant. The idea was right; it didn't survive sustained maintenance, modern board churn, and — plausibly — Node-RED's own JS-based success pulling mindshare away from FBP specifically. Worth taking seriously as a reason to get "why would this one stick" right, not just the technical design.

**ESPHome and Tasmota** are the dominant "no-code" firmware options for ESP-class chips today, but they are configuration-driven (YAML, or a fixed rule engine plus Berry scripting in Tasmota's case), not visual dataflow editors, and they target smart-home use cases specifically rather than general-purpose logic.

Thingstudio's niche: Node-RED's exact visual/mental model (nodes, wires, live values, one-click deploy) combined with a live, standalone-once-deployed on-device runtime, aimed at ESP32 and RP2040/RP2350. MicroFlo already proved this combination is technically viable and didn't achieve sustained adoption doing it; the wager here is that MicroPython's ecosystem, tooling maturity, and modern board support give this attempt a materially better shot than C++03-on-2013-Arduino did — a wager worth naming explicitly rather than assuming.

**Target audience**: the same demographic Node-RED itself serves — home-automation tinkerers and IoT/automation professionals already comfortable with flow-based tools, MQTT, and JSON, who want a fast test/modify/deploy loop — not the education/beginner-programming audience that Scratch-derived block tools like MicroBlocks primarily serve. That framing has a direct design consequence already reflected in §5: a compile-and-flash cycle (XOD's and node-red-mcu's approach) is a worse fit for this audience's iteration-speed expectations than a live interpreter, even at the cost of some runtime performance.

## 3. Target hardware

**Minimum system requirement: ESP32-C3 or comparable** — single-core RISC-V @160MHz, 400KB SRAM, ~4MB flash, WiFi + Bluetooth LE. This is the floor for the ESP32 family, not a suggestion: it rules out ESP8266 (already out of scope — well below 400KB SRAM) and ESP32-S2 (WiFi-only, no Bluetooth — falls short of the BLE requirement even though its RAM/flash are otherwise comparable). Classic ESP32 and ESP32-S3 both clear the C3 bar comfortably (more RAM, dual-core) and remain in scope as higher-spec options within the same family.

| Target | RAM | Flash | Notes |
|---|---|---|---|
| ESP32-C3 | 400KB SRAM | 4MB typical | single-core RISC-V, WiFi + BLE — the baseline the rest of the family is measured against |
| ESP32 (classic), ESP32-S3 | 320KB–512KB SRAM | 4MB+ typical | dual-core Xtensa, WiFi + BLE; more headroom than C3, same minimum-spec logic applies |
| ~~ESP32-S2~~ | 320KB SRAM | 4MB typical | WiFi only, no Bluetooth LE — below the minimum bar, excluded |
| RP2040 (Pico/Pico W) | 264KB SRAM | 2MB (typical board) | dual-core Cortex-M0+; below the C3 RAM baseline (264KB vs. 400KB) but kept in scope for price/ecosystem reasons — see note below |
| RP2350 (Pico 2) | 520KB SRAM | 4MB (typical board) | dual-core M33 or Hazard3; clears the C3 baseline comfortably |

ESP32-C3 (or a higher-spec family member) is the recommended bring-up target: it's the cheapest board that clears the minimum bar, with native WiFi and BLE for both flow deployment and network-facing nodes. RP2040 is the accepted minimum for the Pico family — the C3 floor (400KB SRAM, BLE) applies within the ESP32 family, not project-wide, so RP2040's lower RAM (264KB) and lack of native BLE are accepted trade-offs rather than disqualifying. This is a provisional call: if RP2040's headroom proves too tight once real flows and the MicroPython + `uasyncio` footprint are running on it (§5), the fallback is to raise the Pico-family floor to RP2350 (520KB) the same way ESP32-S2 was excluded on the ESP32 side. Worth revisiting once v1 bring-up data exists rather than deciding blind now.

## 4. System architecture

Three components, talking over a swappable transport:

**Editor** — a browser-based canvas application (no install) where flows are built, node values are inspected live, and deploys are triggered. Runs entirely client-side against a connected device; no server component is required for the core loop, though a companion server/relay is a reasonable v2 addition for team use, remote fleets, or OTA distribution. Flows save to a local file via the File System Access API (Chrome/Edge) with manual export/import as the fallback where that API isn't available (Safari, Firefox), rather than living only in browser storage or a proprietary cloud — the point being that a flow file sits in an ordinary directory the user can `git init` and commit themselves (see §6).

**Transport** — the link between editor and device: USB serial (WebSerial in-browser, no drivers on Chrome/Edge) for the primary bring-up experience, with BLE (Web Bluetooth) and WiFi (local mDNS-discovered device, HTTP/WebSocket) as later additions for untethered deployment. MicroBlocks and most WebSerial-based tools (e.g., the MakeCode/CircuitPython ecosystem) validate that serial-over-USB is a reliable, low-friction default; wireless transports layer on top once the protocol is stable.

**Device runtime** — the on-device virtual machine: a bytecode interpreter, a fixed table of native node implementations (GPIO, timers, math, I2C/SPI, network, etc.), a scheduler for concurrent flow execution, and a thin protocol handler that accepts flow updates and streams live values back.

```
 ┌─────────────────────┐        serial / BLE / WiFi        ┌───────────────────────┐
 │   Browser Editor     │ ───────────────────────────────▶  │   Device Runtime (MCU) │
 │  canvas + node       │ ◀─────────────────────────────── │  VM + scheduler +      │
 │  palette + inspector │     live values, logs, status     │  native node table     │
 └─────────────────────┘                                    └───────────────────────┘
```

## 5. Execution model: on-device VM

The device ships a single runtime image once, flashed like any firmware. After that, flows are pushed as data (a compact bytecode/graph representation), not as new firmware, so redeploying a flow is a protocol message, not a flash cycle.

Design points, adopting MicroPython as the on-device interpreter rather than a bespoke bytecode VM:

MicroBlocks and node-red-mcu both justify a small custom VM/engine on memory grounds, but a bespoke instruction set means building and maintaining a compiler, an interpreter, and a driver library from nothing. MicroPython already has mature, actively-maintained ports for both target chip families (ESP32, RP2040/RP2350), a large existing driver ecosystem for I2C/SPI sensors and peripherals that a node library can wrap directly instead of reimplementing, and — the deciding factor — `uasyncio`, a built-in, well-tested async/await scheduler that maps naturally onto Node-RED's event-driven flow model (each node or triggered subgraph becomes a coroutine/task on the event loop, rather than a hand-rolled cooperative scheduler). The editor compiles the graph to Python source targeting a constrained subset (no dynamic features the node model doesn't need), then precompiles it with `mpy-cross` into `.mpy` bytecode before it's sent to the device — the device never runs the Python compiler itself, which keeps both RAM use and deploy latency down and mirrors MicroPython's own "frozen bytecode" pattern.

Where that compile step runs matters for the "browser-only, no install" claim in §4, and it's resolved rather than assumed: `mpy-cross` is a small, self-contained C program with no host-OS dependencies beyond the C standard library, and there's working precedent for running it as WebAssembly — MicroPython's own `ports/wasm` build target compiles the core runtime to WASM, and the micro:bit Foundation has a working tech demo doing the same for `mpy-cross` specifically. The editor bundles a WASM build of `mpy-cross` and runs the compile step client-side; no local helper process or native binary is required. The ongoing cost is build maintenance — the WASM build needs rebuilding and testing against each MicroPython version bump, which is a CI responsibility, not a one-time integration.

The scheduler is `uasyncio`'s event loop directly: each node (or, more likely, each independently-triggered subgraph — a timer, a GPIO interrupt, a network message) is a coroutine that runs to its next `await` and yields control. This gets Node-RED-style event-driven concurrency without building and debugging a custom scheduler, at the cost of `uasyncio`'s own RAM and flash footprint (roughly 16–64KB depending on port and configuration per the MicroPython docs) — negligible against the RAM available on both target platforms.

Live values are supported by having the VM optionally tag node outputs for reporting — when the editor has a flow open, the device streams a throttled sample of values back over the transport so wires "light up" with real data, the same feedback loop that makes Node-RED and MicroBlocks pleasant to use.

Fault isolation: an uncaught exception inside a node's coroutine is caught at the per-task boundary — `uasyncio` surfaces exceptions on task completion rather than letting them propagate — instead of crashing the whole event loop. The failing subgraph's task stops and reports a structured error back over the transport (node ID, exception type and message) for the editor's inspector to surface (§8); the rest of the flow keeps running. A device-side watchdog is a separate, coarser backstop for the case where the VM itself wedges — an infinite loop inside a node body that never hits an `await` — rather than a clean exception; the watchdog resets the device and the last-deployed flow resumes from flash, same as any power-cycle recovery.

Persistence covers two different things worth keeping distinct. The last-deployed flow's bytecode and static data live in flash so the device resumes the flow after power loss without the editor being connected, matching the "unplug from the laptop, run on battery" behavior MicroBlocks already delivers. Separately, user-facing runtime state — the value held by a variable get/set node, a calibration constant a node computes and wants to keep — lives in its own flash-backed key/value area, keyed by node ID, distinct from the flow bytecode. The default is that this state survives a flow redeploy (a running average shouldn't reset just because the flow was tweaked and pushed again); a node can opt out and request its state be cleared on every deploy where that default is wrong. The editor can read this store back over the transport for inspection, but it's runtime data, not versioned flow source.

## 6. Flow / graph representation

Flows are authored as a JSON graph — nodes with typed properties, edges connecting an output port on one node to an input port on another — deliberately close to Node-RED's own `flows.json` shape, since that model is already well understood and there's no reason to reinvent it. The editor's in-browser compiler walks this graph and emits the compact bytecode/table representation the device actually consumes; the JSON graph itself is the thing saved, versioned, and diffed, never sent to the device directly. The compiled `.mpy` bytecode is a build artifact, not something checked in — same relationship as source code to a compiled binary, and worth calling out explicitly since it's easy to accidentally treat the deploy payload as the source of truth instead of the graph.

Git-friendliness is a first-class requirement for the file format, not just a side effect of using JSON. Node-RED's own `flows.json` is a known cautionary tale here: node position (`x`/`y`) lives in the same object as the node's logic and configuration, so dragging a node on the canvas produces a diff indistinguishable from a real logic change, and two people editing different parts of a flow collide on the same lines constantly. Thingstudio's flow file should split those concerns — a `nodes`/`edges` section that only changes when behavior changes, and a separate `layout` section (positions, canvas viewport, visual grouping) that only changes when someone rearranges the canvas — so a `git diff` on a flow file tells you something meaningful, and two people moving different nodes around don't generate a merge conflict on an unrelated logic change. Serialization needs to be deterministic (stable key ordering, stable node ordering by ID rather than by insertion or canvas position, consistent indentation) so re-saving an untouched flow produces a zero-diff, not the git-blame equivalent of noise. A project directory holds as many flow files as needed — one flow per device (below) doesn't mean one flow per repo; a fleet of devices is naturally a directory of flow files, each independently diffable and reviewable.

Node categories for v1: GPIO in/out and PWM, timers/intervals, boolean and arithmetic logic, comparators/thresholds, I2C/SPI peripheral nodes (starting with a handful of common sensors), simple state (variable get/set), WiFi status and basic HTTP request, and MQTT publish/subscribe — the last promoted to a firm v1 node rather than a maybe, since it's the dominant integration path into this audience's existing Node-RED/Home-Assistant setups and doesn't depend on WiFi being the *deploy* transport, only on the chip having a radio, already true for every in-scope target per §3. Inject (manually or on-schedule fire a test message into a flow) and debug (print a value to the editor's inspector) are called out by name rather than left as generic examples, since together they're most of what makes the test/modify/deploy loop feel fast, not just a side effect of live redeploy.

The function node runs actual (precompiled) MicroPython rather than an invented expression language — simpler to build, since the interpreter already exists, and more useful to this audience, since it's real, searchable Python rather than a bespoke syntax to learn. It isn't sandboxed against its own author: a function node can do anything any other node's native code can do, which is an acceptable trust boundary given §9 already treats deploy access as the security perimeter — the flow author is the same person who could already write a malicious native node if they controlled the toolchain. The one thing it's guarded against is accidentally, not maliciously, hanging the device: the same watchdog from §5 that catches a wedged native node catches a function node stuck in a loop that never yields.

Message model: wires carry a `msg` envelope — `payload` (the primary value), `topic` (a routing/identification string), and arbitrary extra properties a node can attach — rather than bare typed values, deliberately matching Node-RED's own model instead of inventing a new one. This is foundational, not a v1-only shortcut: every node's input/output contract is built around the envelope from the start, since changing the wire format later would break every node ever written against it. `payload` itself is typed from a small fixed set — `int`, `number` (float), `bool`, `string`, `bytes`, `any` — and the editor still checks `payload` type compatibility at wire-connect time (an `int` output can feed a `number` input, a `bytes` output can't feed a `string` input without an explicit conversion node, and the editor refuses the connection outright); the envelope adds routing and metadata on top of that, it doesn't replace the type check.

A few asks from this audience's feature wishlist are deliberately deferred past v1 to keep the initial build small, checked against the architecture rather than assumed to be fine: config nodes with per-device override (a shared template plus small per-device values — unique topic prefix, calibration constant — fits the git-friendly multi-file layout above once built; v1 ships with plain per-flow-file values and no sharing/override mechanism yet); a catch/error node the flow itself can react to (§5's fault isolation already catches exceptions at the per-task boundary and reports them over the protocol — routing that same exception into a catch-node's coroutine instead of, or alongside, the `NODE_ERROR` message is additive to that model whenever it's built, not a redesign); a self-hosted mini dashboard, gauge/switch/chart served from the device's own HTTP stack (needs an on-device HTTP server and a new UI-node category, both additive to the node-category and native-module extensibility model in §7 rather than requiring rework — deferred because it's a genuinely larger chunk of work than the rest of this list); and Home Assistant auto-discovery (a thin convenience layer on top of the MQTT node already in v1 — an HA-aware node that publishes the right discovery config alongside the data — deferred since generic MQTT already lets this audience wire up HA manually in v1, just with a few more steps).

Single flow per device for v1 is a scope choice, not an architecture limit — worth correcting explicitly, since an earlier draft of this section implied the `uasyncio` model made concurrent independent flows hard. It doesn't: every node/subgraph is already just a coroutine on one shared event loop (§5), and the scheduler makes no distinction between "two flows' tasks" and "one flow's tasks" — running flow A and flow B concurrently on one device is already what the runtime does, structurally, for free — and it's worth being precise that this is the only option, not just the simplest one: MicroPython's `uasyncio` has a single global event loop with no multi-loop or per-`Runner` isolation (`new_event_loop()` resets that same loop's state rather than creating an independent one), and even RP2040/RP2350's second core can't host its own loop under standard `uasyncio`. A genuinely isolated per-flow runtime — separate loops, separate crash domains — isn't on the table on this platform without stepping well outside `uasyncio` into something like running an entire second MicroPython instance on the other core, which isn't a supported or documented pattern and isn't worth pursuing for the isolation §5's per-task exception boundary already provides. If RP2040/RP2350's second core ever gets used for real (offloading blocking work via `_thread` rather than a second event loop), Peter Hinch's `micropython-async` project has the documented-correct threadsafe primitives (`ThreadSafeQueue`, `ThreadSafeEvent`) for that specific hazard — noted here rather than adopted now; see §11. What multiple independently-deployed flows actually needs, and what v1 is deferring, is bookkeeping around that, not new scheduling machinery: node IDs need to be globally unique across every flow on a device rather than just within one (the standard choice anyway, and it makes the state-persistence and error-keying in §5 work unchanged with no per-flow namespacing required); `DEPLOY` needs to scope which node IDs it's replacing rather than assuming "the whole device" (a small protocol addition, §13); and the editor needs to track cumulative RAM/flash budget across every flow already deployed to a device, not just the one currently being edited, since `HELLO`'s free-space report (§13) only tells you what's left right now, not what happens once a second flow's footprint lands on top of a first one already running. The other real gap is pin/peripheral conflicts: two independently-authored flows can both claim the same GPIO or I2C bus with nothing catching it until runtime, since the editor generally only has one flow file open at a time, whereas a single combined flow lets the graph itself make that visible at author-time. None of that is a scheduling problem — it's editor tooling and protocol bookkeeping, reasonable to place in v2 (§10) rather than v1, but it's a smaller and cheaper lift than "genuinely independent multi-tasking flows are the hard version" made it sound.

## 7. Extensibility

Choosing MicroPython as the runtime changes this from a limitation into one of the stronger arguments for the approach. Node definitions have two halves: a small JSON descriptor for the editor (palette entry, ports, property UI) and a Python module implementing the node's behavior. Because node logic is ordinary (precompiled) Python rather than something baked into the firmware image, adding a new node type is a matter of pushing a new `.mpy` module to the device's filesystem alongside the flow, not rebuilding and reflashing the runtime — much closer to Node-RED's install-a-node-and-go model than a native-code VM allows. Existing MicroPython drivers for common I2C/SPI sensors can generally be wrapped as a node with only a thin adapter, rather than ported from scratch.

The exception is performance- or timing-critical nodes (tight PWM/bit-banging, high-rate sampling), where a pure-Python implementation may be too slow; MicroPython's support for C-native modules and the `@micropython.native`/viper code emitters gives an escape hatch for those cases without abandoning the rest of the model.

## 8. Deployment and live debugging

Deploy is a diff, not a full reflash where avoidable: on "Deploy," the editor compiles the graph, and (at least for small edits) the device can patch only what changed rather than reloading the whole flow, though a v1 can reasonably start with "replace the whole flow" and optimize later. The status/log/inspector panel shows connection state, per-node errors, and live port values, the same role Node-RED's debug sidebar and MicroBlocks' variable watchers play.

## 9. Security considerations

The transport should authenticate before accepting a flow write, particularly once WiFi transport exists — an unauthenticated "push arbitrary bytecode to any device on the network" primitive is a meaningful risk. USB and BLE proximity provide a natural first factor; WiFi deployment should require a pairing step (e.g., a code shown on-device or a first-use-over-USB provisioning flow) rather than trusting anything on the local network by default. This is a v2-scope concern for WiFi transport specifically; USB serial in v1 has physical access as its natural gate. The same perimeter covers the unsandboxed function node from §6: anyone who can deploy a flow could already ship a malicious native node, so an unrestricted Python function node doesn't widen the trust boundary, it just makes using it less effort.

## 10. Phased roadmap

Before v1: three independent proof-of-concept spikes de-risk the core assumptions this roadmap depends on — see §15.

A reasonable v1 (bring-up): ESP32-C3 (or a higher-spec ESP32-family member) only, USB serial (WebSerial) transport, the v1 node set from §6 (GPIO, timers, logic, math, one or two common I2C sensors, inject, debug, a real-MicroPython function node, WiFi status/HTTP request, MQTT), full-flow redeploy (no diffing), live value streaming, flow persistence across power cycles. This is enough to validate the central bet — does a live on-device VM plus a Node-RED-style canvas actually feel good to use — before investing in wireless transport, node diffing, or additional chip targets.

v2 candidates, roughly in order of likely value: RP2040/RP2350 support, BLE and WiFi transport with pairing/auth, config nodes with per-device override (§6), a catch/error node (§6), Home Assistant auto-discovery on top of the v1 MQTT node (§6), incremental flow updates instead of full redeploy. v3+: a self-hosted mini dashboard (§6), multi-device flows (one flow spanning devices via network nodes), and a companion server for team libraries and fleet deployment.

## 11. Open questions

Several decisions are deliberately left open pending prototyping rather than settled here: standard MicroPython versus CircuitPython as the base port (CircuitPython trades some `uasyncio`/library compatibility for a friendlier USB/driver story on some boards, worth a direct comparison before committing); whether the node-editor canvas should be built on an existing library (Litegraph.js and Drawflow are the leading lightweight options; both are lighter-weight than adapting Blockly, which is block-stack-oriented rather than free node/wire) or built bespoke; whether generated flow code should stay human-readable Python (debuggable, but larger before `mpy-cross` compilation) or a more compact intermediate form; and whether the unsandboxed function node from §6 ever warrants hardening (restricting available imports/builtins) beyond the watchdog's crash-loop protection — the working assumption is no, since §9 already treats deploy access as the trust perimeter, but worth revisiting if Thingstudio ever supports something like shared/marketplace flows written by someone other than the deployer.

Deliberately deferred until after the first POC rather than decided now: whether to adopt Peter Hinch's `micropython-async` (MIT-licensed, builds on stock `asyncio` v3 rather than replacing it, so low switching cost either way) for its hardware driver primitives (switches/buttons/ADC/encoders — relevant to §6's GPIO nodes), its `ThreadSafeQueue`/`ThreadSafeEvent` primitives (relevant to the second-core note above), its cron-like scheduler (relevant to a future scheduling node), `aiorepl` (relevant to §13's live-value/state-inspection story), and `asyncio_alt`, its lightly-modified low-latency/lightsleep event loop variant (relevant to live-value latency and to power/sleep management generally, which this doc doesn't address yet anywhere and should pick up as its own open item once the POC is done). None of it is needed to answer the POC's actual question — does the core live-redeploy loop work and feel good — so evaluating and adopting specific pieces is real post-POC work, not a POC dependency.

A few more surfaced while specifying §5/§6/§13 and are deliberately deferred rather than resolved here, as lower-priority than what's now settled: how node definitions themselves are distributed and versioned between editor and device (§7 covers how a node gets pushed once you have it, not where it comes from or how a version mismatch between an editor's expectation and a device's installed node is caught); whether a no-hardware simulation mode is worth building, for development and onboarding without a board attached; and how updating the runtime image itself (MicroPython plus the node library, distinct from redeploying a flow) actually works mechanically — OTA vs. USB-only is still open. One piece of that is now decided rather than open, though: a major-version runtime update is allowed to wipe the deployed flow and persisted state (§5) if the new runtime isn't compatible with what's on the device — recovery is just redeploying the flow file from git, which is exactly the case the git-friendly format above exists for. Minor/patch runtime updates should preserve the deployed flow. That major/minor/patch distinction is what the protocol version field in §13 needs to carry.

## 12. Licensing and open-source suitability

Open-sourcing the project is a design constraint, not an afterthought: every third-party component it depends on should carry an OSI-approved license, permissive (MIT/BSD/Apache-2.0) by default, so the whole stack can be released without copyleft obligations or legal ambiguity. The dependencies proposed elsewhere in this doc check out against that bar:

| Component | Role | License | Notes |
|---|---|---|---|
| MicroPython (core VM, `uasyncio`, `mpy-cross`) | on-device runtime | MIT | permissive, no concerns |
| ESP-IDF | ESP32 port substrate | Apache-2.0 | the framework itself is Apache-2.0; see caveat below on WiFi/BT binary blobs |
| FreeRTOS | RTOS underlying the ESP32 port | MIT | permissive since the v10.4+ relicense |
| lwIP | TCP/IP stack (ESP-IDF, RP2040 WiFi) | modified BSD | permissive |
| Raspberry Pi Pico SDK | RP2040/RP2350 port substrate | BSD-3-Clause | permissive |
| Litegraph.js or Drawflow | browser canvas/node-editor library | MIT (both) | either is a clean pick; final choice per §11 |
| WebSerial / Web Bluetooth | browser transport APIs | n/a (browser platform APIs, not distributed code) | no license implication |

One caveat worth flagging rather than glossing over: Espressif distributes the ESP32 WiFi/Bluetooth and RF-calibration libraries as precompiled binary blobs bundled inside ESP-IDF. The redistribution terms are Apache-2.0, so using them imposes no license *obligation* conflict — but the blobs themselves are not source-available, so "open source" for an ESP32 build is accurate at the license-compliance level while not being fully source-auditable at the radio-stack layer. That's a preexisting limitation of the ESP32 platform itself (MicroPython, ESPHome, and everyone else building on ESP-IDF inherits it too), not something specific to this design, but it's worth being upfront about if the project's open-source pitch implies full source availability rather than just license compliance. RP2040/RP2350 builds don't have this issue for WiFi (the Pico W's WiFi driver situation differs by SDK version and is worth a separate check when that target is scoped).

Two things worth doing before any public release rather than assuming this table stays accurate: run an automated license scan (e.g., an SPDX-based checker) over the actual dependency tree once it's pinned, since indirect dependencies pulled in by the MicroPython build or editor tooling (npm packages, etc.) aren't audited above; and treat this section as engineering due diligence, not legal advice — a proper release-readiness check should include an actual legal review, particularly for the ESP-IDF blob question if the project wants to make explicit claims about full source availability.

## 13. Wire protocol (v1 sketch)

Concrete enough to build against, not a frozen spec. Framing: length-prefixed frames over the raw transport — a 2-byte length header plus payload, kept identical across serial/BLE/WiFi so higher layers don't need to know which transport they're on — with a 1-byte message type and a CBOR-encoded body. CBOR over JSON mainly for size and on-device decode cost; JSON's simplicity may still be worth the overhead for v1 debuggability, and that trade is worth revisiting once real payload sizes are measured rather than assumed.

Message types covering the v1 scope already committed to elsewhere in this doc: `HELLO` (device announces chip type, MicroPython/runtime version, and free flash/RAM on connect, so the editor can warn before a flow is too big for the target); `DEPLOY` (full flow bytecode plus static data, replacing whatever's currently deployed, matching §8's "start with full-flow redeploy" call); `DEPLOY_ACK` / `DEPLOY_ERROR` (success, or a structured compile/space error); `VALUE_STREAM` (device → editor, throttled live port values while the editor has a flow open, per §5); `NODE_ERROR` (device → editor, the fault-isolation report from §5 — node ID plus exception type/message); `STATE_READ` / `STATE_WRITE` (inspecting or editing the persisted variable store from §5 without a full redeploy).

Deliberately not fixed yet: authentication/pairing handshake fields, which depend on the WiFi pairing design in §9 not being detailed enough yet to commit a wire format to; and the exact mechanics of the runtime-image OTA/USB-update process itself (still open, §11). One thing that *is* fixed now: `HELLO` reports the runtime version as major.minor.patch, not a single opaque number, so the editor can tell "compatible, safe DEPLOY" apart from "major mismatch, DEPLOY may wipe the flow and state store per §5/§11" and warn the user before it happens rather than after.

## 14. Project license and governance

The project itself should ship under a single, permissive license applied consistently across the repo. Recommendation: Apache-2.0 over MIT, mainly for the explicit patent grant — an embedded/wireless project sits closer to patent-sensitive territory than typical web tooling, and Apache-2.0's grant (each contributor licenses their own patent claims covering their contribution) gives downstream users real protection MIT doesn't provide. It also matches the license already used by ESP-IDF, the largest single dependency in the stack, so there's no license-family mismatch to explain to contributors. This is worth treating as a confirmed decision rather than a default, though — MIT remains entirely reasonable if minimizing license text and process overhead matters more than the patent grant.

Repo structure: a single monorepo (editor, device runtime glue, node library) is the simpler starting point given the pieces are tightly coupled right now — a node's editor descriptor and its device-side Python module change together — and splitting into separate editor/runtime/node-library repos is a reasonable v2 move once there's an actual external contributor base wanting to work on one piece independently. Vendored third-party code (Litegraph.js or Drawflow, MicroPython itself if forked rather than tracked as a submodule) keeps its own upstream license file per §12's audit; that coexists with the project's own license choice and doesn't complicate it.

## 15. Proof-of-concept scope

Three independent spikes, not one POC — each tests a separate risk in this doc, none depends on the others finishing first, and none needs to be "production-shaped." §10's v1 bring-up starts only once these have actually answered their questions, not before.

### 15.1 POC-A: core runtime + redeploy loop (the one that matters most)

**Question it answers:** does a live MicroPython/`uasyncio` runtime on real hardware, driven from a browser, deliver an edit→deploy→see-it-run loop that's fast and actually feels good — the central bet in §1.

**In scope:** one real ESP32-C3 board (not a simulator); a hand-written (not compiler-generated) MicroPython program with at least two concurrent `uasyncio` coroutines — a timer loop toggling a GPIO output, and a second loop polling a GPIO input or ADC and printing its value — to confirm the concurrency model in §5 behaves as designed under real conditions, not just on paper; deploy as raw `.py` source text over WebSerial, `exec()`'d directly on-device, explicitly skipping `mpy-cross`/bytecode (that's POC-B, kept separate on purpose — see below); a crude ad hoc text protocol, not §13's CBOR framing; a throwaway browser page with a couple of hardcoded buttons and a raw serial console, not a real editor.

**Out of scope:** the graph compiler, the node/wire canvas, `mpy-cross`/WASM, the real §13 protocol, fault isolation, state persistence, git file format, MQTT, multi-flow.

**Success criteria:** repeatable, measured wall-clock time from "hit deploy" to observable behavior change (target: comfortably under a second, matching §1's claim, not just "eventually works"); `gc.mem_free()` sampled before/after to sanity-check §3's RAM assumptions against real numbers instead of datasheet arithmetic; both coroutines demonstrably keep running independently after a redeploy; no crash or memory creep across on the order of 50 consecutive redeploys without a power cycle. This is also the milestone where the raw-text-vs-precompiled-bytecode decision flagged in §5 gets an actual answer instead of an assumption.

**Results (2026-08-10, LuatOS CORE-ESP32-C3):** run against a hand-written harness/payload pair (`poc-a/` in the repo — `harness.py` is the one-time-flashed exec listener, `payload.py` is the two-coroutine test program, `index.html` the WebSerial page) with no wiring beyond the board's onboard LEDs (GPIO12/13) and BOOT button (GPIO9). Deploy → observable behavior change (click → first GPIO toggle): **99ms**. Deploy → protocol ack (click → `DEPLOY_OK`): **97ms avg / 98ms max** across a 50-redeploy stress run. `gc.mem_free()` held steady around **168KB free** throughout, comfortable headroom against the 400KB SRAM baseline in §3. Both coroutines kept running correctly after every redeploy. The 50-redeploy stress run was **50/50 clean** — no crash, no timeout — with a net `gc.mem_free()` drift of **-80 bytes** over all 50 cycles, i.e. noise, not creep. Both latency numbers land roughly 10x under the "comfortably under a second" target, confirming §1's central bet on this hardware. On the raw-text-vs-bytecode question flagged in §5: at this program's size, raw-source `exec()` is fast enough on its own that deploy latency doesn't force POC-B's precompiled-bytecode path — that call can be made on other grounds (RAM headroom at larger program sizes, parse-error surface, etc.) rather than deploy speed.

### 15.2 POC-B: `mpy-cross`-to-WASM toolchain spike

**Question it answers:** does `mpy-cross` actually run client-side in a browser as WASM, per the precedent cited in §5 — confirming the "browser-only, no install" claim in §4 rather than assuming it from someone else's tech demo.

**In scope:** build or adapt an existing WASM build of `mpy-cross` (starting point: the precedent already cited in §5's sources); a minimal browser harness that compiles a small hardcoded Python snippet to `.mpy` bytecode entirely client-side; validate the output is real, correct bytecode — either by round-tripping it through a stock desktop `mpy-cross`/MicroPython install, or, as a stretch goal, feeding it to POC-A's device over its serial link and confirming it executes.

**Out of scope:** the graph compiler (feeding it real generated code, not hand-written snippets), the node library, any UI polish.

**Success criteria:** the WASM module loads and compiles valid bytecode in a real Chrome/Edge tab; compile latency for a small snippet is fast enough to be invisible in a deploy click (target: comfortably under 100ms); bundle size and any special hosting requirements (e.g., cross-origin isolation headers, if the build needs threads) are known quantities instead of open risk.

**Results (2026-08-11, Chrome, `poc-b/` in the repo &mdash; `mpy-cross.wasm`/`mpy-cross.mjs` the built artifacts, `index.html` the self-contained harness):** built `mpy-cross` as WASM by cross-compiling stock `micropython/micropython` (commit `3a89fc2411`, 2026-08-10) with Emscripten, adapting rather than reusing the build recipe from &sect;5's cited precedent (the micro:bit Foundation repo builds a full micro:bit-firmware toolchain in-browser, of which only its `mpy-cross`-specific Makefile flags were relevant; it also compiles from a micro:bit-specific MicroPython fork, whereas Thingstudio needs stock ESP32/RP2040 MicroPython). No source changes to MicroPython were required. Confirmed the WASM build loads and compiles in an actual Chrome tab (not just Node) with zero console errors and exactly one network request for the whole page. Compile latency for the hardcoded test snippet: **8.9ms** on the first (cold) compile, **avg 0.87ms / min 0.20ms / max 12.5ms** across a 50-compile benchmark &mdash; roughly two orders of magnitude under the "comfortably under 100ms" target. WASM module instantiation: 17.2ms. Bundle size: **353KB** (`mpy-cross.wasm`) + **67KB** (glue JS), ~410KB combined uncompressed as a real build would serve them as separate static assets. No special hosting requirements: the build uses no threads (no `-pthread`/`SharedArrayBuffer`), so no COOP/COEP cross-origin-isolation headers are needed, contrary to what's sometimes required for WASM builds that do use threads &mdash; a plain static file server is sufficient. Output correctness was validated by compiling the same snippet with a native desktop `mpy-cross` build from the identical commit and comparing: **byte-for-byte identical (SHA-256 match)**, not just plausibly-correct output. (Running the compiled `.mpy` end-to-end on a native MicroPython interpreter was also attempted to close the loop further, but the quickest-to-build unix-port variant turned out not to have `.mpy` loading compiled in at all — a variant-config gap unrelated to WASM correctness, confirmed by the native build's own output hitting the identical error. The hardware round-trip stretch goal wasn't attempted; no POC-A device was available in this environment. Neither gap weakens the byte-identical result above, which is the validation this success criterion actually calls for.) All three success criteria are met cleanly; see `poc-b/README.md` for the full build recipe and validation detail.

### 15.3 POC-C: node/wire canvas feel spike

**Question it answers:** does a node/wire dataflow canvas — as opposed to Node-RED's own editor, or a block-based one like MicroBlocks' — actually feel good to author in for this specific audience (§2's target-audience framing), independent of whether anything real is running behind it.

**In scope:** a throwaway integration of Litegraph.js and/or Drawflow (both MIT-licensed per §12, both candidates per §11) with a handful of representative fake node types — GPIO out, inject, MQTT publish, function node, debug — wired only to placeholder behavior, no compiler or device involved; exercising the basic interactions a Node-RED user already expects: drag, wire, type-mismatch rejection (can be mocked), zoom/pan, node property editing, multi-select.

**Out of scope:** the real compiler, the real `msg` envelope/type system, any persistence beyond the browser session, any device connection.

**Success criteria:** mostly qualitative — does it feel at least as good to build a small flow here as in Node-RED itself — plus one concrete technical checkpoint: does Litegraph.js or Drawflow integrate cleanly enough for this node model without a large amount of custom canvas code, settling §11's open "which library" question with evidence instead of a guess.

### 15.4 Sequencing

All three can start in parallel — none blocks another. POC-A is the one worth prioritizing if only one can run first, since it tests the riskiest and most foundational assumption in the whole doc; POC-B and POC-C are cheaper, browser-only spikes that de-risk specific later decisions (the toolchain claim in §5, the editor-library choice in §11) without needing hardware or each other. A natural, optional follow-on once all three land: merge POC-A's transport with POC-B's compiled bytecode (deploying real `.mpy` instead of raw text) as the actual start of §10's v1, rather than treating that merge as part of the POC phase itself.
