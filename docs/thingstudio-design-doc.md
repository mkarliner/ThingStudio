# Thingstudio — Design Document

**A drag-and-drop, low-code environment for programming microcontrollers**

Status: draft v0.1 · 2026-08-09

## 1. Vision

Thingstudio is a browser-based, node-and-wire visual programming environment, in the spirit of Node-RED, whose output runs directly on a microcontroller rather than on a server. A user drags nodes onto a canvas — sensors, GPIO, timers, logic, math, network — wires them together, and pushes the resulting flow to a physically connected or networked device. The device then runs the flow autonomously, with no host machine required afterward.

The core bet that differentiates Thingstudio from most prior art: flows are interpreted live by a small on-device virtual machine rather than compiled to native firmware. This trades a small amount of runtime performance for the thing that makes Node-RED itself so productive — editing a running system without a flash-and-reboot cycle, seeing live values on the wires, and swapping a flow in under a second.

## 2. Prior art and positioning

Several projects already occupy pieces of this space. Understanding what they do well — and where they fall short of "Node-RED for MCUs" — shapes the design choices below.

**Node-RED MCU Edition** (phoddie/node-red-mcu) is the closest existing analog. It runs actual Node-RED flows on microcontrollers by compiling them against the Moddable XS JavaScript engine, targeting ESP32 and a handful of other chips. It proves the concept is viable, but it works by cross-compiling a flow into a firmware image ahead of time — closer to "compile Node-RED to firmware" than a live, always-running on-device interpreter. There is no live-editing loop once a device is deployed; the workflow is still edit-compile-flash. It also validates that a general-purpose language VM (there, Moddable's XS engine for JS) is a workable foundation for this kind of tool; Thingstudio makes the same bet with MicroPython instead, for its broader board support and existing driver/sensor ecosystem (see §5, §7).

**MicroBlocks** is the strongest existing example of the live-interpreter model this project wants to follow. It is a Scratch-style block language with its own on-device bytecode VM, runs on ESP32, RP2040/Pico, micro:bit, and others, supports up to ten concurrent scripts, and lets you click a block in the browser and watch it execute on the board immediately. Its limitation for this project's purposes is the programming model: Scratch-style stacked blocks are excellent for sequential/event logic but don't represent dataflow (wires carrying live values between nodes) as directly as a Node-RED-style graph does.

**XOD** is a node-based dataflow language for Arduino/microcontrollers, closer to Thingstudio's visual metaphor (nodes and wires, not stacked blocks), but it generates native C++ and flashes a full firmware image per change — no live device interaction, no runtime flow updates.

**MicroFlo** is the one existing project that already combined exactly this trio — a node/wire dataflow editor (via Flowhub, the NoFlo-based FBP visual tool), a runtime that executes standalone on the microcontroller, and live introspection/reconfiguration without reflashing. It's a decade-old proof that the idea works: real deployments (a fridge thermostat, an LED installation) ran unattended for years starting in 2013. It's also a cautionary tale rather than a solved problem — its own README rates its status as "minimally useful," board support tops out at ESP8266 and pre-2015 Cortex-M0–M4/AVR8 parts (nothing in the ESP32 family), it's written in C++03 without exceptions or the standard library, and by every visible signal (220 stars, no sign of recent activity) it's dormant. The idea was right; it didn't survive sustained maintenance, modern board churn, and — plausibly — Node-RED's own JS-based success pulling mindshare away from FBP specifically. Worth taking seriously as a reason to get "why would this one stick" right, not just the technical design.

**ESPHome and Tasmota** are the dominant "no-code" firmware options for ESP-class chips today, but they are configuration-driven (YAML, or a fixed rule engine plus Berry scripting in Tasmota's case), not visual dataflow editors, and they target smart-home use cases specifically rather than general-purpose logic.

Thingstudio's niche: Node-RED's exact visual/mental model (nodes, wires, live values, one-click deploy) combined with a live, standalone-once-deployed on-device runtime, aimed at ESP32 and RP2040/RP2350. MicroFlo already proved this combination is technically viable and didn't achieve sustained adoption doing it; the wager here is that MicroPython's ecosystem, tooling maturity, and modern board support give this attempt a materially better shot than C++03-on-2013-Arduino did — a wager worth naming explicitly rather than assuming.

**Target audience**: the same demographic Node-RED itself serves — home-automation tinkerers and IoT/automation professionals already comfortable with flow-based tools, MQTT, and JSON, who want a fast test/modify/deploy loop — not the education/beginner-programming audience that Scratch-derived block tools like MicroBlocks primarily serve. That framing has a direct design consequence already reflected in §5: a compile-and-flash cycle (XOD's and node-red-mcu's approach) is a worse fit for this audience's iteration-speed expectations than a live interpreter, even at the cost of some runtime performance.

## 3. Target hardware

**Minimum system requirement: ESP32-C3 or comparable** — single-core RISC-V @160MHz, 400KB SRAM, ~4MB flash, WiFi + Bluetooth LE. This is the floor for the ESP32 family, not a suggestion: it rules out ESP8266 (already out of scope — well below 400KB SRAM) and ESP32-S2 (WiFi-only, no Bluetooth — falls short of the BLE requirement even though its RAM/flash are otherwise comparable). Classic ESP32 and ESP32-S3 both clear the C3 bar comfortably (more RAM, dual-core) and remain in scope as higher-spec options within the same family.

| Target | RAM | Flash | Notes |
|---|---|---|---|
| ESP32-C3 | 400KB SRAM | 4MB typical | single-core RISC-V, WiFi + BLE — the baseline the rest of the family is measured against |
| ESP32 (classic), ESP32-S3 | 320KB–512KB SRAM | 4MB+ typical | dual-core Xtensa, WiFi + BLE; more headroom than C3, same minimum-spec logic applies |
| ~~ESP32-S2~~ | 320KB SRAM | 4MB typical | WiFi only, no Bluetooth LE — below the minimum bar, excluded |
| RP2040 (Pico/Pico W) | 264KB SRAM | 2MB (typical board) | dual-core Cortex-M0+; below the C3 RAM baseline (264KB vs. 400KB) but kept in scope for price/ecosystem reasons — see note below |
| RP2350 (Pico 2) | 520KB SRAM | 4MB (typical board) | dual-core M33 or Hazard3; clears the C3 baseline comfortably |

ESP32-C3 (or a higher-spec family member) is the recommended bring-up target: it's the cheapest board that clears the minimum bar, with native WiFi and BLE for both flow deployment and network-facing nodes. RP2040 is the accepted minimum for the Pico family — the C3 floor (400KB SRAM, BLE) applies within the ESP32 family, not project-wide, so RP2040's lower RAM (264KB) and lack of native BLE are accepted trade-offs rather than disqualifying. This is a provisional call: if RP2040's headroom proves too tight once real flows and the MicroPython + `uasyncio` footprint are running on it (§5), the fallback is to raise the Pico-family floor to RP2350 (520KB) the same way ESP32-S2 was excluded on the ESP32 side. Worth revisiting once v1 bring-up data exists rather than deciding blind now.

## 4. System architecture

Three components, talking over a swappable transport:

**Editor** — a browser-based canvas application where flows are built, node values are inspected live, and deploys are triggered. ~~Runs entirely client-side against a connected device; no server component is required for the core loop, though a companion server/relay is a reasonable v2 addition for team use, remote fleets, or OTA distribution.~~ **superseded 2026-08-16 (`working-notes/rete-migration-decision.md`, Decision 2): a thin local backend, Node-RED's model, not a pure-browser app.** The backend owns serial I/O, flow-file I/O, and static serving; the compiler and `mpy-cross` WASM build stay client-side, unchanged from the description below. This wasn't a packaging preference — a pure-browser architecture makes "backend runs wherever the devices are, a human drives the editor from a browser somewhere else" structurally impossible (`navigator.serial` is a local-hardware API), and that remote-access case is the decisive argument, not "team use" or "OTA distribution" as originally framed here. It also promotes the "companion server/relay" this sentence used to describe as a later v2 maybe to something the architecture already provides from v1 — see `rete-migration-decision.md` for the full reasoning, including why Electron/Tauri were both ruled out (still just as tied to the machine they run on) and the two supported deployment postures (network-secured/localhost-behind-a-VPN as the default, app-secured/LAN-exposed as explicit opt-in) this implies for §9. **Addendum, 2026-08-16 (later same session): this doesn't retire the pure-browser WebSerial path — it's kept as a deliberate, frozen fallback,** scoped to local-only use with no remote access and no auth story (the original trust model below still applies to it unchanged), while all new investment goes into the backend path. The editor requires an **explicit user choice** between "direct" (WebSerial, local-only) and "via backend" connection modes — not auto-detection, which would fail silently and ambiguously in exactly the way CLAUDE.md's fault-handling priority warns against (can't tell "no backend running" apart from "backend slow/misconfigured" without telling the user which one happened). See `working-notes/deployment-and-distribution-notes.md` for the reasoning. Flows save to a local file via the File System Access API (Chrome/Edge) with manual export/import as the fallback where that API isn't available (Safari, Firefox), rather than living only in browser storage or a proprietary cloud — the point being that a flow file sits in an ordinary directory the user can `git init` and commit themselves (see §6). Under the backend model this becomes the backend's own filesystem access rather than the File System Access API specifically, but the git-friendly-directory requirement is unchanged.

**Transport** — the link between editor and device: USB serial (WebSerial in-browser, no drivers on Chrome/Edge) for the primary bring-up experience, with BLE (Web Bluetooth) and WiFi (local mDNS-discovered device, HTTP/WebSocket) as later additions for untethered deployment. MicroBlocks and most WebSerial-based tools (e.g., the MakeCode/CircuitPython ecosystem) validate that serial-over-USB is a reliable, low-friction default; wireless transports layer on top once the protocol is stable.

**Device runtime** — the on-device virtual machine: a bytecode interpreter, a fixed table of native node implementations (GPIO, timers, math, I2C/SPI, network, etc.), a scheduler for concurrent flow execution, and a thin protocol handler that accepts flow updates and streams live values back.

```
 ┌─────────────────────┐        serial / BLE / WiFi        ┌───────────────────────┐
 │   Browser Editor     │ ───────────────────────────────▶  │   Device Runtime (MCU) │
 │  canvas + node       │ ◀─────────────────────────────── │  VM + scheduler +      │
 │  palette + inspector │     live values, logs, status     │  native node table     │
 └─────────────────────┘                                    └───────────────────────┘
```

## 5. Execution model: on-device VM

The device ships a single runtime image once, flashed like any firmware. After that, flows are pushed as data (a compact bytecode/graph representation), not as new firmware, so redeploying a flow is a protocol message, not a flash cycle.

Design points, adopting MicroPython as the on-device interpreter rather than a bespoke bytecode VM:

MicroBlocks and node-red-mcu both justify a small custom VM/engine on memory grounds, but a bespoke instruction set means building and maintaining a compiler, an interpreter, and a driver library from nothing. MicroPython already has mature, actively-maintained ports for both target chip families (ESP32, RP2040/RP2350), a large existing driver ecosystem for I2C/SPI sensors and peripherals that a node library can wrap directly instead of reimplementing, and — the deciding factor — `uasyncio`, a built-in, well-tested async/await scheduler that maps naturally onto Node-RED's event-driven flow model (each node or triggered subgraph becomes a coroutine/task on the event loop, rather than a hand-rolled cooperative scheduler). The editor compiles the graph to Python source targeting a constrained subset (no dynamic features the node model doesn't need), then precompiles it with `mpy-cross` into `.mpy` bytecode before it's sent to the device — the device never runs the Python compiler itself, which keeps both RAM use and deploy latency down and mirrors MicroPython's own "frozen bytecode" pattern. This is a hard ceiling, not just an efficiency win: MicroPython's own compiler needs RAM on top of whatever the resulting code needs, so on-device compilation of a large enough source file can fail outright (OOM) on a memory-constrained board even though the identical code runs fine once it's bytecode — a real, recurring failure mode from pre-`mpy-cross`-era MicroPython use (MQTT client libraries were a common trigger), not a hypothetical one. See §15.1's POC-A results for how this settles the raw-source-vs-bytecode question in favor of precompiled bytecode.

Where that compile step runs matters for the "browser-only, no install" claim in §4, and it's resolved rather than assumed: `mpy-cross` is a small, self-contained C program with no host-OS dependencies beyond the C standard library, and there's working precedent for running it as WebAssembly — MicroPython's own `ports/wasm` build target compiles the core runtime to WASM, and the micro:bit Foundation has a working tech demo doing the same for `mpy-cross` specifically. The editor bundles a WASM build of `mpy-cross` and runs the compile step client-side; no local helper process or native binary is required. The ongoing cost is build maintenance — the WASM build needs rebuilding and testing against each MicroPython version bump, which is a CI responsibility, not a one-time integration.

The scheduler is `uasyncio`'s event loop directly: each node (or, more likely, each independently-triggered subgraph — a timer, a GPIO interrupt, a network message) is a coroutine that runs to its next `await` and yields control. This gets Node-RED-style event-driven concurrency without building and debugging a custom scheduler, at the cost of `uasyncio`'s own RAM and flash footprint (roughly 16–64KB depending on port and configuration per the MicroPython docs) — negligible against the RAM available on both target platforms.

Live values are supported by having the VM optionally tag node outputs for reporting — when the editor has a flow open, the device streams a throttled sample of values back over the transport so wires "light up" with real data, the same feedback loop that makes Node-RED and MicroBlocks pleasant to use.

Fault isolation: an uncaught exception inside a node's coroutine is caught at the per-task boundary — `uasyncio` surfaces exceptions on task completion rather than letting them propagate — instead of crashing the whole event loop. The failing subgraph's task stops and reports a structured error back over the transport (node ID, exception type and message) for the editor's inspector to surface (§8); the rest of the flow keeps running. A device-side watchdog is a separate, coarser backstop for the case where the VM itself wedges — an infinite loop inside a node body that never hits an `await` — rather than a clean exception; the watchdog resets the device and the last-deployed flow resumes from flash, same as any power-cycle recovery.

This per-task fault isolation covers deployed flow tasks; it deliberately doesn't cover the transport/protocol handler task itself, which needs the same property for a different reason — added here after POC-D (§15.5) hit exactly this gap on real hardware. That listener task necessarily owns the raw transport stream and, per §9, disables the normal interrupt-character escape hatch while it does (stray protocol bytes shouldn't be able to trigger a KeyboardInterrupt mid-transfer) — which means if the listener task itself dies from an unhandled exception, there is no REPL to fall back to and no way to attempt another `DEPLOY`; only a physical reflash recovers it. POC-D's harness demonstrated the failure concretely (an old harness version choked on a binary frame it didn't understand, and its listener task died silently with no recovery path) and now carries two independent mitigations worth carrying into the real runtime: the listener's own dispatch loop must never be allowed to exit on an unhandled exception (every phase wrapped, logged as a structured error, loop continues) and every blocking read within it should be time-bounded rather than able to hang indefinitely on a partial/garbled transfer. A boot-time window where the interrupt character is still live (a few seconds before the runtime commits to taking over the transport) is a second, physical-access-independent fallback layer on top of that, not a replacement for it. Whether the real v1 runtime needs all of this or just the try/except hardening is worth revisiting once §13's actual `HELLO` version handshake exists — a version-checked editor refusing to send a `DEPLOY` the device can't parse prevents this specific trigger before it starts, though not the general class of "the listener task must survive whatever it's sent."

Persistence covers two different things worth keeping distinct. The last-deployed flow's bytecode and static data live in flash so the device resumes the flow after power loss without the editor being connected, matching the "unplug from the laptop, run on battery" behavior MicroBlocks already delivers. Separately, user-facing runtime state — the value held by a variable get/set node, a calibration constant a node computes and wants to keep — lives in its own flash-backed key/value area, keyed by node ID, distinct from the flow bytecode. The default is that this state survives a flow redeploy (a running average shouldn't reset just because the flow was tweaked and pushed again); a node can opt out and request its state be cleared on every deploy where that default is wrong. The editor can read this store back over the transport for inspection, but it's runtime data, not versioned flow source.

## 6. Flow / graph representation

Flows are authored as a JSON graph — nodes with typed properties, edges connecting an output port on one node to an input port on another — deliberately close to Node-RED's own `flows.json` shape, since that model is already well understood and there's no reason to reinvent it. The editor's in-browser compiler walks this graph and emits the compact bytecode/table representation the device actually consumes; the JSON graph itself is the thing saved, versioned, and diffed, never sent to the device directly. The compiled `.mpy` bytecode is a build artifact, not something checked in — same relationship as source code to a compiled binary, and worth calling out explicitly since it's easy to accidentally treat the deploy payload as the source of truth instead of the graph.

Git-friendliness is a first-class requirement for the file format, not just a side effect of using JSON. Node-RED's own `flows.json` is a known cautionary tale here: node position (`x`/`y`) lives in the same object as the node's logic and configuration, so dragging a node on the canvas produces a diff indistinguishable from a real logic change, and two people editing different parts of a flow collide on the same lines constantly. Thingstudio's flow file should split those concerns — a `nodes`/`edges` section that only changes when behavior changes, and a separate `layout` section (positions, canvas viewport, visual grouping) that only changes when someone rearranges the canvas — so a `git diff` on a flow file tells you something meaningful, and two people moving different nodes around don't generate a merge conflict on an unrelated logic change. Serialization needs to be deterministic (stable key ordering, stable node ordering by ID rather than by insertion or canvas position, consistent indentation) so re-saving an untouched flow produces a zero-diff, not the git-blame equivalent of noise. A project directory holds as many flow files as needed — one flow per device (below) doesn't mean one flow per repo; a fleet of devices is naturally a directory of flow files, each independently diffable and reviewable.

Node categories for v1: GPIO in/out and PWM, timers/intervals, boolean and arithmetic logic, comparators/thresholds, I2C/SPI peripheral nodes (starting with a handful of common sensors), simple state (variable get/set), WiFi status and basic HTTP request, and MQTT publish/subscribe — the last promoted to a firm v1 node rather than a maybe, since it's the dominant integration path into this audience's existing Node-RED/Home-Assistant setups and doesn't depend on WiFi being the *deploy* transport, only on the chip having a radio, already true for every in-scope target per §3. Inject (manually or on-schedule fire a test message into a flow) and debug (print a value to the editor's inspector) are called out by name rather than left as generic examples, since together they're most of what makes the test/modify/deploy loop feel fast, not just a side effect of live redeploy.

The function node runs actual (precompiled) MicroPython rather than an invented expression language — simpler to build, since the interpreter already exists, and more useful to this audience, since it's real, searchable Python rather than a bespoke syntax to learn. It isn't sandboxed against its own author: a function node can do anything any other node's native code can do, which is an acceptable trust boundary given §9 already treats deploy access as the security perimeter — the flow author is the same person who could already write a malicious native node if they controlled the toolchain. The one thing it's guarded against is accidentally, not maliciously, hanging the device: the same watchdog from §5 that catches a wedged native node catches a function node stuck in a loop that never yields.

Message model: wires carry a `msg` envelope — `payload` (the primary value), `topic` (a routing/identification string), and arbitrary extra properties a node can attach — rather than bare typed values, deliberately matching Node-RED's own model instead of inventing a new one. This is foundational, not a v1-only shortcut: every node's input/output contract is built around the envelope from the start, since changing the wire format later would break every node ever written against it. `payload` itself is typed from a small fixed set — `int`, `number` (float), `bool`, `string`, `bytes`, `any` — and the editor still checks `payload` type compatibility at wire-connect time (an `int` output can feed a `number` input, a `bytes` output can't feed a `string` input without an explicit conversion node, and the editor refuses the connection outright); the envelope adds routing and metadata on top of that, it doesn't replace the type check.

A few asks from this audience's feature wishlist are deliberately deferred past v1 to keep the initial build small, checked against the architecture rather than assumed to be fine: config nodes with per-device override (a shared template plus small per-device values — unique topic prefix, calibration constant — fits the git-friendly multi-file layout above once built; v1 ships with plain per-flow-file values and no sharing/override mechanism yet); a catch/error node the flow itself can react to (§5's fault isolation already catches exceptions at the per-task boundary and reports them over the protocol — routing that same exception into a catch-node's coroutine instead of, or alongside, the `NODE_ERROR` message is additive to that model whenever it's built, not a redesign); a self-hosted mini dashboard, gauge/switch/chart served from the device's own HTTP stack (needs an on-device HTTP server and a new UI-node category, both additive to the node-category and native-module extensibility model in §7 rather than requiring rework — deferred because it's a genuinely larger chunk of work than the rest of this list); and Home Assistant auto-discovery (a thin convenience layer on top of the MQTT node already in v1 — an HA-aware node that publishes the right discovery config alongside the data — deferred since generic MQTT already lets this audience wire up HA manually in v1, just with a few more steps).

**Addendum, 2026-08-17 (`working-notes/tier1-node-candidates-prioritization-briefing.md`'s reprioritization session): two concrete motivating cases for the on-device HTTP server above, worth having on hand rather than left abstract next time this deferral is reweighed.** On-demand log retrieval — a device buffers debug/log output while disconnected, retrievable via an explicit request once reachable again — needs a real server because retrieval has to work independent of an active editor session, not just the wire protocol's `STATE_READ`-style mechanism (§13), which only serves a connected editor. And a Tasmota-style AP/captive-portal mode, letting a device with no configured WiFi credentials serve its own configuration page, which also touches §9's own already-deferred WiFi-pairing/provisioning design — the same future on-device-HTTP-server work motivates both, not two independent asks. Neither changes the deferral itself; both were checked against it deliberately rather than folded in as if they were v1-sized (see the working note for the full reasoning, including why file ops — the other candidate reviewed this session — turned out to have no remaining use case once its own motivating cases were traced to this item and to the flash-backed state store below, rather than needing a dedicated filesystem-access node).

**Addendum, 2026-08-17 (same session): Tier 1 item 5's node-category resolution.** Full per-candidate reasoning in `working-notes/mvp-feature-priorities.md`'s Tier 1 item 5; the parts that actually change this section's committed v1 list:

- **GPIO input is event-driven (interrupt/pin-change), not polling.** The original `gpio_in` node (poll-driven, landed under Tier 1 item 2) is deprecated — a periodic *read* isn't architecturally an "input" in the sense this section means (a node generating a message in response to an external event); it's a `timer` + `function` read, same shape as ADC below, and shouldn't have been a dedicated node. The genuine GPIO input is interrupt/pin-change (`machine.Pin.irq()`, bridged safely into `uasyncio`), still filed under this section's existing "GPIO in/out and PWM" category — no new category, but a real correction to what "GPIO in" means. Debounce ships as a property on it (cooldown algorithm — ignore transitions within N ms of the last accepted one — chosen deliberately over the heavier settle-and-confirm alternative, per `CLAUDE.md`'s "no premature optimization, but don't paint into a dead end" principle).
- **ADC needs no node at all.** A `machine.ADC(pin).read_u16()`-shaped call (exact call board/mode-dependent) belongs in a function node's own code, same as any other one-off peripheral read that doesn't need to originate a flow's timing on its own.
- **Raw UDP/TCP sockets are promoted to a firm v1 node, on the same explicit-reasoning footing MQTT got above** — genuinely new v1 surface beyond "basic HTTP request": UDP send/receive (connectionless; receive is event-driven, not polled) and TCP send/listen-receive (connection-oriented; send is one-shot request/response shaped like the existing HTTP request node, with a lazy-expiry connection-reuse cache; listen-receive is event-driven via `uasyncio.start_server`, bounded by a `maxConnections` property against resource exhaustion). Deliberately not validating payload content on either — the wire format is undefined by design, and this project isn't taking on a firewall role — though an open listening port remains a real, acknowledged attack-surface fact.
- **Filter/event compression joins inject and debug as a named v1 pattern** (change-only forwarding, rate-limiting) rather than left as a generic possibility — small, general-purpose, no new compiler capability needed.
- **mDNS moves to §10's v2 list** (added there) — a discovery convenience, not a functional gap, and its MicroPython support isn't yet confirmed across every in-scope target the way sockets/HTTP already are.

Single flow per device for v1 is a scope choice, not an architecture limit — worth correcting explicitly, since an earlier draft of this section implied the `uasyncio` model made concurrent independent flows hard. It doesn't: every node/subgraph is already just a coroutine on one shared event loop (§5), and the scheduler makes no distinction between "two flows' tasks" and "one flow's tasks" — running flow A and flow B concurrently on one device is already what the runtime does, structurally, for free — and it's worth being precise that this is the only option, not just the simplest one: MicroPython's `uasyncio` has a single global event loop with no multi-loop or per-`Runner` isolation (`new_event_loop()` resets that same loop's state rather than creating an independent one), and even RP2040/RP2350's second core can't host its own loop under standard `uasyncio`. A genuinely isolated per-flow runtime — separate loops, separate crash domains — isn't on the table on this platform without stepping well outside `uasyncio` into something like running an entire second MicroPython instance on the other core, which isn't a supported or documented pattern and isn't worth pursuing for the isolation §5's per-task exception boundary already provides. If RP2040/RP2350's second core ever gets used for real (offloading blocking work via `_thread` rather than a second event loop), Peter Hinch's `micropython-async` project has the documented-correct threadsafe primitives (`ThreadSafeQueue`, `ThreadSafeEvent`) for that specific hazard — noted here rather than adopted now; see §11. What multiple independently-deployed flows actually needs, and what v1 is deferring, is bookkeeping around that, not new scheduling machinery: node IDs need to be globally unique across every flow on a device rather than just within one (the standard choice anyway, and it makes the state-persistence and error-keying in §5 work unchanged with no per-flow namespacing required); `DEPLOY` needs to scope which node IDs it's replacing rather than assuming "the whole device" (a small protocol addition, §13); and the editor needs to track cumulative RAM/flash budget across every flow already deployed to a device, not just the one currently being edited, since `HELLO`'s free-space report (§13) only tells you what's left right now, not what happens once a second flow's footprint lands on top of a first one already running. The other real gap is pin/peripheral conflicts: two independently-authored flows can both claim the same GPIO or I2C bus with nothing catching it until runtime, since the editor generally only has one flow file open at a time, whereas a single combined flow lets the graph itself make that visible at author-time. None of that is a scheduling problem — it's editor tooling and protocol bookkeeping, reasonable to place in v2 (§10) rather than v1, but it's a smaller and cheaper lift than "genuinely independent multi-tasking flows are the hard version" made it sound.

## 7. Extensibility

Choosing MicroPython as the runtime changes this from a limitation into one of the stronger arguments for the approach. Node definitions have two halves: a small JSON descriptor for the editor (palette entry, ports, property UI) and a Python module implementing the node's behavior. Because node logic is ordinary (precompiled) Python rather than something baked into the firmware image, adding a new node type is a matter of pushing a new `.mpy` module to the device's filesystem alongside the flow, not rebuilding and reflashing the runtime — much closer to Node-RED's install-a-node-and-go model than a native-code VM allows. Existing MicroPython drivers for common I2C/SPI sensors can generally be wrapped as a node with only a thin adapter, rather than ported from scratch.

The exception is performance- or timing-critical nodes (tight PWM/bit-banging, high-rate sampling), where a pure-Python implementation may be too slow; MicroPython's support for C-native modules and the `@micropython.native`/viper code emitters gives an escape hatch for those cases without abandoning the rest of the model.

See `working-notes/node-definition-model.md` for the concrete node-authoring contract this section describes in the abstract — worked out from POC-D's actual compiler and node definitions, generalized into what the real §6 compiler needs per node type, and cross-referenced with §11's now-resolved call that v1's node set ships fixed inside the runtime image rather than distributed separately.

## 8. Deployment and live debugging

Deploy is a diff, not a full reflash where avoidable: on "Deploy," the editor compiles the graph, and (at least for small edits) the device can patch only what changed rather than reloading the whole flow, though a v1 can reasonably start with "replace the whole flow" and optimize later. The status/log/inspector panel shows connection state, per-node errors, and live port values, the same role Node-RED's debug sidebar and MicroBlocks' variable watchers play.

## 9. Security considerations

The transport should authenticate before accepting a flow write, particularly once WiFi transport exists — an unauthenticated "push arbitrary bytecode to any device on the network" primitive is a meaningful risk. USB and BLE proximity provide a natural first factor; WiFi deployment should require a pairing step (e.g., a code shown on-device or a first-use-over-USB provisioning flow) rather than trusting anything on the local network by default. ~~This is a v2-scope concern for WiFi transport specifically; USB serial in v1 has physical access as its natural gate.~~ **invalidated 2026-08-16 (`working-notes/rete-migration-decision.md` Decision 2, `working-notes/transport-auth-design.md`): physical access no longer gates the deploy path.** §4's backend runs wherever the devices are, reachable remotely by design — a USB-connected device is exposed to whoever can reach the backend, not whoever can reach the cable. Board-runtime auth stops being defense in depth behind USB's physical perimeter and becomes the only perimeter left if the backend is compromised or misconfigured, so this is a day-1 v1 concern now, not deferred to WiFi/v2.

**Correction, 2026-08-16 (later same session): the paragraph above
overgeneralized.** §4's addendum kept the pure-browser WebSerial path as a
deliberate, frozen, local-only fallback alongside the backend-mediated
path, not retired — and physical access *does* still gate that specific
mode, unchanged from the original reasoning, precisely because there's no

invalidation above applies to backend-mediated deploys specifically, which

paired with a backend is exposed to whoever can reach that backend even if

**v1 mechanism: HMAC-SHA256 over a shared secret, with a persisted monotonic counter in place of a random challenge nonce** — reserved in `HELLO` (`authRequired`/`authScheme` fields) even in a v1 that ships `authRequired: false`, so a downgrade attack can't later be mistaken for "this device predates auth." The counter, not a nonce, is the deliberate choice: this project's target hardware (§3) already spans multiple chip families with no uniform RNG guarantee across them, and a mechanism that needs no on-device entropy at all sidesteps auditing every current and future target's RNG quality individually, rather than trusting a specific chip's random-number peripheral. Full mechanism, alternatives considered (including why a public/private keypair — the better long-term answer — costs a firmware rebuild for v1 without a threat model that justifies it yet), and what's deliberately deferred (WiFi pairing/provisioning, the backend's own editor-facing auth, confidentiality/TLS) in `working-notes/transport-auth-design.md`.

The same perimeter covers the unsandboxed function node from §6: anyone who can deploy a flow could already ship a malicious native node, so an unrestricted Python function node doesn't widen the trust boundary, it just makes using it less effort.

## 10. Phased roadmap

Before v1: three independent proof-of-concept spikes de-risk the core assumptions this roadmap depends on — see §15.

A reasonable v1 (bring-up): ESP32-C3 (or a higher-spec ESP32-family member) only, USB serial (WebSerial) transport, the v1 node set from §6 (GPIO, timers, logic, math, one or two common I2C sensors, inject, debug, a real-MicroPython function node, WiFi status/HTTP request, MQTT), full-flow redeploy (no diffing), live value streaming, flow persistence across power cycles. This is enough to validate the central bet — does a live on-device VM plus a Node-RED-style canvas actually feel good to use — before investing in wireless transport, node diffing, or additional chip targets.

v2 candidates, roughly in order of likely value: RP2040/RP2350 support, BLE and WiFi transport with pairing/auth, config nodes with per-device override (§6), a catch/error node (§6), Home Assistant auto-discovery on top of the v1 MQTT node (§6), incremental flow updates instead of full redeploy, mDNS device/service discovery (§6 addendum, 2026-08-17 — deferred because MicroPython mDNS support isn't yet confirmed across every in-scope target in §3, not for lack of use case), and a TCP client node's proactive (closes-even-if-idle) connection expiry, on top of the lazy-expiry version shipping in v1 (§6 addendum). v3+: a self-hosted mini dashboard (§6), multi-device flows (one flow spanning devices via network nodes), and a companion server for team libraries and fleet deployment.

Open-sourcing the project is a design constraint, not an afterthought: every third-party component it depends on should carry an OSI-approved license, permissive (MIT/BSD/Apache-2.0) by default, so the whole stack can be released without copyleft obligations or legal ambiguity. The dependencies proposed elsewhere in this doc check out against that bar:

One caveat worth flagging rather than glossing over: Espressif distributes the ESP32 WiFi/Bluetooth and RF-calibration libraries as precompiled binary blobs bundled inside ESP-IDF. The redistribution terms are Apache-2.0, so using them imposes no license *obligation* conflict — but the blobs themselves are not source-available, so "open source" for an ESP32 build is accurate at the license-compliance level while not being fully source-auditable at the radio-stack layer. ## 13. Wire protocol (v1 sketch)

Concrete enough to build against, not a frozen spec. Framing: length-prefixed frames over the raw transport — a 2-byte length header plus payload, kept identical across serial/BLE/WiFi so higher layers don't need to know which transport they're on — with a 1-byte message type and a CBOR-encoded body. CBOR over JSON mainly for size and on-device decode cost; JSON's simplicity may still be worth the overhead for v1 debuggability, and that trade is worth revisiting once real payload sizes are measured rather than assumed.

Message types covering the v1 scope already committed to elsewhere in this doc: `HELLO` (device announces chip type, MicroPython/runtime version, free flash/RAM on connect, and — as of 2026-08-16, see below — auth capability, so the editor can warn before a flow is too big for the target); `DEPLOY` (full flow bytecode plus static data, replacing whatever's currently deployed, matching §8's "start with full-flow redeploy" call); `DEPLOY_ACK` / `DEPLOY_ERROR` (success, or a structured compile/space error); `VALUE_STREAM` (device → editor, throttled live port values while the editor has a flow open, per §5); `NODE_ERROR` (device → editor, the fault-isolation report from §5 — node ID plus exception type/message); `STATE_READ` / `STATE_WRITE` (inspecting or editing the persisted variable store from §5 without a full redeploy).

~~Deliberately not fixed yet: authentication/pairing handshake fields, which depend on the WiFi pairing design in §9 not being detailed enough yet to commit a wire format to~~ **partially fixed 2026-08-16 (`working-notes/transport-auth-design.md`): `HELLO` gains two required fields even in a v1 that ships without auth enforced — `authRequired` (bool) and `authScheme` (string; `"none"` for v1-without-auth, `"hmac-sha256-ctr"` for the mechanism §9 now specifies).** This is the one-way door: a `HELLO` that says nothing about auth capability can't later be told apart from a device whose auth requirement was stripped by an attacker, and that's unfixable retroactively — every already field-deployed device would need a manual reflash to become distinguishable. The actual `auth` payload on `DEPLOY`/`STATE_WRITE` (scheme, counter, MAC) is deliberately *not* fixed yet — it's additive to the existing codecs (unknown extra keys are already ignored, unknown message types already degrade to a logged, recoverable error) and can be designed when the mechanism is actually built rather than now. WiFi pairing's own handshake fields remain genuinely deferred, unchanged, pending §9's WiFi pairing design. The exact mechanics of the runtime-image OTA/USB-update process itself is also still open (§11). One thing that *is* fixed now: `HELLO` reports the runtime version as major.minor.patch, not a single opaque number, so the editor can tell "compatible, safe DEPLOY" apart from "major mismatch, DEPLOY may wipe the flow and state store per §5/§11" and warn the user before it happens rather than after.

## 14. Project license and governance

The project itself should ship under a single, permissive license applied consistently across the repo. Recommendation: Apache-2.0 over MIT, mainly for the explicit patent grant — an embedded/wireless project sits closer to patent-sensitive territory than typical web tooling, and Apache-2.0's grant (each contributor licenses their own patent claims covering their contribution) gives downstream users real protection MIT doesn't provide. It also matches the license already used by ESP-IDF, the largest single dependency in the stack, so there's no license-family mismatch to explain to contributors. This is worth treating as a confirmed decision rather than a default, though — MIT remains entirely reasonable if minimizing license text and process overhead matters more than the patent grant.

Repo structure: a single monorepo (editor, device runtime glue, node library) is the simpler starting point given the pieces are tightly coupled right now — a node's editor descriptor and its device-side Python module change together — and splitting into separate editor/runtime/node-library repos is a reasonable v2 move once there's an actual external contributor base wanting to work on one piece independently. Vendored third-party code (MicroPython itself if forked rather than tracked as a submodule) keeps its own upstream license file per §12's audit; that coexists with the project's own license choice and doesn't complicate it.

## 15. Proof-of-concept scope

Three independent spikes, not one POC — each tests a separate risk in this doc, none depends on the others finishing first, and none needs to be "production-shaped." §10's v1 bring-up starts only once these have actually answered their questions, not before.

### 15.1 POC-A: core runtime + redeploy loop (the one that matters most)

**Question it answers:** does a live MicroPython/`uasyncio` runtime on real hardware, driven from a browser, deliver an edit→deploy→see-it-run loop that's fast and actually feels good — the central bet in §1.

**In scope:** one real ESP32-C3 board (not a simulator); a hand-written (not compiler-generated) MicroPython program with at least two concurrent `uasyncio` coroutines — a timer loop toggling a GPIO output, and a second loop polling a GPIO input or ADC and printing its value — to confirm the concurrency model in §5 behaves as designed under real conditions, not just on paper; deploy as raw `.py` source text over WebSerial, `exec()`'d directly on-device, explicitly skipping `mpy-cross`/bytecode (that's POC-B, kept separate on purpose — see below); a crude ad hoc text protocol, not §13's CBOR framing; a throwaway browser page with a couple of hardcoded buttons and a raw serial console, not a real editor.

**Out of scope:** the graph compiler, the node/wire canvas, `mpy-cross`/WASM, the real §13 protocol, fault isolation, state persistence, git file format, MQTT, multi-flow.

**Success criteria:** repeatable, measured wall-clock time from "hit deploy" to observable behavior change (target: comfortably under a second, matching §1's claim, not just "eventually works"); `gc.mem_free()` sampled before/after to sanity-check §3's RAM assumptions against real numbers instead of datasheet arithmetic; both coroutines demonstrably keep running independently after a redeploy; no crash or memory creep across on the order of 50 consecutive redeploys without a power cycle. This is also the milestone where the raw-text-vs-precompiled-bytecode decision flagged in §5 gets an actual answer instead of an assumption.

**Results (2026-08-10, LuatOS CORE-ESP32-C3):** run against a hand-written harness/payload pair (`pocs/poc-a/` in the repo — `harness.py` is the one-time-flashed exec listener, `payload.py` is the two-coroutine test program, `index.html` the WebSerial page) with no wiring beyond the board's onboard LEDs (GPIO12/13) and BOOT button (GPIO9). Deploy → observable behavior change (click → first GPIO toggle): **99ms**. Deploy → protocol ack (click → `DEPLOY_OK`): **97ms avg / 98ms max** across a 50-redeploy stress run. `gc.mem_free()` held steady around **168KB free** throughout, comfortable headroom against the 400KB SRAM baseline in §3. Both coroutines kept running correctly after every redeploy. The 50-redeploy stress run was **50/50 clean** — no crash, no timeout — with a net `gc.mem_free()` drift of **-80 bytes** over all 50 cycles, i.e. noise, not creep. Both latency numbers land roughly 10x under the "comfortably under a second" target, confirming §1's central bet on this hardware. On the raw-text-vs-bytecode question flagged in §5: at this program's size, raw-source `exec()` is fast enough on its own that deploy latency doesn't force POC-B's precompiled-bytecode path — that call can be made on other grounds (RAM headroom at larger program sizes, parse-error surface, etc.) rather than deploy speed. **Resolved 2026-08-12 (MVP planning review): precompiled `.mpy` bytecode, on exactly the RAM-headroom ground flagged above.** On-device compilation isn't just slower than shipping bytecode, it can fail outright — MicroPython's own compiler needs RAM on top of whatever the resulting code needs, and large-enough source (MQTT client libraries were a real, recurring trigger for this in pre-`mpy-cross`-era MicroPython use) can OOM the compile step on a memory-constrained board even though the identical code runs fine once it's bytecode. This confirms §5's already-stated design (compile client-side, precompile with `mpy-cross`, device never runs the Python compiler) rather than changing it — POC-A's raw-`exec()` path was correctly scoped as a POC-only shortcut (this section's own out-of-scope list already excludes `mpy-cross`), not a real v1 deploy mode.

### 15.2 POC-B: `mpy-cross`-to-WASM toolchain spike

**Question it answers:** does `mpy-cross` actually run client-side in a browser as WASM, per the precedent cited in §5 — confirming the "browser-only, no install" claim in §4 rather than assuming it from someone else's tech demo.

**In scope:** build or adapt an existing WASM build of `mpy-cross` (starting point: the precedent already cited in §5's sources); a minimal browser harness that compiles a small hardcoded Python snippet to `.mpy` bytecode entirely client-side; validate the output is real, correct bytecode — either by round-tripping it through a stock desktop `mpy-cross`/MicroPython install, or, as a stretch goal, feeding it to POC-A's device over its serial link and confirming it executes.

**Out of scope:** the graph compiler (feeding it real generated code, not hand-written snippets), the node library, any UI polish.

**Success criteria:** the WASM module loads and compiles valid bytecode in a real Chrome/Edge tab; compile latency for a small snippet is fast enough to be invisible in a deploy click (target: comfortably under 100ms); bundle size and any special hosting requirements (e.g., cross-origin isolation headers, if the build needs threads) are known quantities instead of open risk.

**Results (2026-08-11, Chrome, `pocs/poc-b/` in the repo &mdash; `mpy-cross.wasm`/`mpy-cross.mjs` the built artifacts, `index.html` the self-contained harness):** built `mpy-cross` as WASM by cross-compiling stock `micropython/micropython` (commit `3a89fc2411`, 2026-08-10) with Emscripten, adapting rather than reusing the build recipe from &sect;5's cited precedent (the micro:bit Foundation repo builds a full micro:bit-firmware toolchain in-browser, of which only its `mpy-cross`-specific Makefile flags were relevant; it also compiles from a micro:bit-specific MicroPython fork, whereas Thingstudio needs stock ESP32/RP2040 MicroPython). No source changes to MicroPython were required. Confirmed the WASM build loads and compiles in an actual Chrome tab (not just Node) with zero console errors and exactly one network request for the whole page. Compile latency for the hardcoded test snippet: **8.9ms** on the first (cold) compile, **avg 0.87ms / min 0.20ms / max 12.5ms** across a 50-compile benchmark &mdash; roughly two orders of magnitude under the "comfortably under 100ms" target. WASM module instantiation: 17.2ms. Bundle size: **353KB** (`mpy-cross.wasm`) + **67KB** (glue JS), ~410KB combined uncompressed as a real build would serve them as separate static assets. No special hosting requirements: the build uses no threads (no `-pthread`/`SharedArrayBuffer`), so no COOP/COEP cross-origin-isolation headers are needed, contrary to what's sometimes required for WASM builds that do use threads &mdash; a plain static file server is sufficient. Output correctness was validated by compiling the same snippet with a native desktop `mpy-cross` build from the identical commit and comparing: **byte-for-byte identical (SHA-256 match)**, not just plausibly-correct output. (Running the compiled `.mpy` end-to-end on a native MicroPython interpreter was also attempted to close the loop further, but the quickest-to-build unix-port variant turned out not to have `.mpy` loading compiled in at all — a variant-config gap unrelated to WASM correctness, confirmed by the native build's own output hitting the identical error. The hardware round-trip stretch goal wasn't attempted; no POC-A device was available in this environment. Neither gap weakens the byte-identical result above, which is the validation this success criterion actually calls for.) All three success criteria are met cleanly; see `pocs/poc-b/README.md` for the full build recipe and validation detail.

### 15.3 POC-C: node/wire canvas feel spike

**Question it answers:** does a node/wire dataflow canvas — as opposed to Node-RED's own editor, or a block-based one like MicroBlocks' — actually feel good to author in for this specific audience (§2's target-audience framing), independent of whether anything real is running behind it.

**In scope:** a throwaway integration of Litegraph.js and/or Drawflow (both MIT-licensed per §12, both candidates per §11) with a handful of representative fake node types — GPIO out, inject, MQTT publish, function node, debug — wired only to placeholder behavior, no compiler or device involved; exercising the basic interactions a Node-RED user already expects: drag, wire, type-mismatch rejection (can be mocked), zoom/pan, node property editing, multi-select.

**Out of scope:** the real compiler, the real `msg` envelope/type system, any persistence beyond the browser session, any device connection.

**Success criteria:** mostly qualitative — does it feel at least as good to build a small flow here as in Node-RED itself — plus one concrete technical checkpoint: does Litegraph.js or Drawflow integrate cleanly enough for this node model without a large amount of custom canvas code, settling §11's open "which library" question with evidence instead of a guess.

**Results (2026-08-11, `pocs/poc-c/` in the repo):** both libraries were built out to the same 5 fake node types (inject, function, gpio out, mqtt out, debug) with identical mocked behavior, for a direct side-by-side — `pocs/poc-c/` (Litegraph.js 0.7.18) and `pocs/poc-c/drawflow/` (Drawflow 0.0.60), both vendored as official MIT-licensed npm builds, pinned and hash-verified against the registry rather than trusted blind. Full comparison and verification detail in `pocs/poc-c/README.md`; summary: Litegraph needed no custom infrastructure to get type-checked wiring (`LiteGraph.isValidConnection` rejects a mismatched wire during the drag itself, before it can be dropped), live value propagation (`graph.start()` + `onExecute` drive the mock GPIO LED/MQTT log/debug sidebar for free), and multi-select (shift/ctrl-click and box-select both native, confirmed working after fixing a real config mistake made along the way — `canvas.multi_select = true` was set thinking it enabled box-select, but it actually made plain clicks additive to the selection, so grabbing one node dragged every previously-clicked node with it; removed). Drawflow needed all three hand-rolled: a hand-written port-type registry plus a `connectionCreated` handler that lets an invalid connection form and then rips it back out (a "flash then reject" UX, not "can't drop it"); a hand-written `propagate()`/`receive()` walk over `editor.export()` to fake dataflow, since Drawflow is an editor only with no execution engine; and multi-select isn't reachable at all — `drawflow.min.js` has no `shiftKey` handling anywhere and only a singular `node_selected` field, confirmed by source inspection and a headless jsdom check, not assumed. Drawflow's real advantages — a ~46KB bundle (Litegraph's is ~491KB) and real-DOM/HTML node bodies (nicer default property-editing ergonomics, no custom widget system) — don't offset building a type system, an execution engine, and multi-select from scratch. On the technical checkpoint specifically, the evidence favors Litegraph clearly. The qualitative half of this success criterion — does it feel as good as Node-RED to actually build a flow — is inherently a hands-on judgment call this writeup can't settle on its own.

### 15.4 Sequencing

All three can start in parallel — none blocks another. POC-A is the one worth prioritizing if only one can run first, since it tests the riskiest and most foundational assumption in the whole doc; POC-B and POC-C are cheaper, browser-only spikes that de-risk specific later decisions (the toolchain claim in §5, the editor-library choice in §11) without needing hardware or each other. A natural, optional follow-on once all three land: merge POC-A's transport with POC-B's compiled bytecode (deploying real `.mpy` instead of raw text) as the actual start of §10's v1, rather than treating that merge as part of the POC phase itself. That follow-on is now POC-D (§15.5), scoped deliberately smaller than v1 rather than treated as v1's actual start — a call made explicitly rather than assumed, since the pipeline merge itself was worth proving before committing to v1's full node set and feature list.

### 15.5 POC-D: canvas → compile → deploy → run

Added 2026-08-11, after POC-A/B/C landed — the follow-on flagged above, given its own scope rather than folded silently into v1.

**Question it answers:** does the full pipeline — author a small flow on the real (Litegraph) canvas, compile the graph to real MicroPython source, cross-compile it client-side to `.mpy` bytecode via POC-B's WASM toolchain, and deploy+run it on real ESP32-C3 hardware over POC-A's WebSerial transport — actually work end to end. Deliberately scoped smaller than a true v1 (§10): enough of the pipeline to prove it holds together, not the full v1 node set, real msg envelope, persistence, or fault isolation.

**In scope:** the same one real ESP32-C3 board as POC-A; an `inject → function → gpio_out` flow, authored on POC-C's Litegraph canvas (trimmed to those 3 node types); a small, deliberately hardcoded (not general-purpose) graph→Python compiler that walks the exported LGraph JSON and emits real MicroPython source — `inject`'s payload/repeat properties become a coroutine, `function`'s `code` property is inlined as a real executed function body (not a JS mock this time), `gpio_out`'s `pin` property becomes a `machine.Pin` write; that generated source cross-compiled client-side to `.mpy` bytecode via POC-B's `mpy-cross.wasm`; deployed over WebSerial to the device, extending POC-A's harness protocol to load and run `.mpy` bytecode instead of `exec()`-ing raw text; a "Deploy" button on the browser page driving the whole chain in one click.

**Out of scope:** the real v1 node set beyond these 3 types (no mqtt, no sensors, no WiFi); the real `msg` envelope/type system beyond the bool-payload case already exercised in POC-C; §13's real wire protocol (still a crude ad hoc one, extended from POC-A's, not CBOR-framed); persistence across power cycles; fault isolation / per-task exception boundaries; live value streaming back to the editor (deferred — success here is "it runs correctly on-device," not "the editor shows live values while it runs").

**Success criteria:** the compiled flow actually runs on the ESP32-C3 and toggles the GPIO pin correctly, driven by the inject node's configured value and repeat interval; the function node's real MicroPython code actually executes on-device (not a mock pass-through); one click on "Deploy" in the browser drives compile → cross-compile → transport → run without manual steps in between; deploy latency is still reasonably fast (no fixed target — this is about closing the loop, not re-proving POC-A's latency numbers). Like POC-A and POC-B, running against real hardware needs to happen on your machine — the page/compiler/harness ship with a run sheet, same pattern as `pocs/poc-a/README.md`/`pocs/poc-b/README.md`.

**Results (2026-08-11, LuatOS CORE-ESP32-C3, same board as POC-A):** the full pipeline works end to end on real hardware — an `inject → function → gpio_out` flow authored on the canvas, compiled client-side to real MicroPython, cross-compiled to real `.mpy` bytecode via POC-B's `mpy-cross.wasm`, deployed over WebSerial, and confirmed physically toggling an onboard LED correctly, tracking the inject node's `payload` value (true/false) across redeploys. All four success criteria are met except the deploy-latency one, which wasn't measured numerically this round (no fixed target existed for it, and getting the pipeline working end to end took priority over instrumenting it) — worth a follow-up pass with real timing similar to POC-A's, but not blocking. Before any hardware was touched, the compiler (4 unit tests) and the mpy-cross handoff (real generated MicroPython actually cross-compiled to valid `.mpy` bytecode under Node, not just a browser tab) were both verified off-device.

Getting from "compiles cleanly off-device" to "actually runs on the board" surfaced a real, useful sequence of hardware-only problems, each fixed in turn rather than glossed over:

- An old POC-A harness was still resident on first connect. It choked on the new binary frame and its listener task died silently (uasyncio's generic "Task exception wasn't retrieved"), with no REPL to fall back to since the runtime deliberately disables Ctrl-C while it owns the transport (§9) — the only recovery was a full `esptool` reflash. Fixed by hardening `harness.py`'s listener so no single bad exchange can kill the task (every phase wrapped, logged, and recoverable) plus a boot-time window where Ctrl-C still works normally before the runtime commits to taking over stdin. Folded into §5's fault-isolation discussion above as a gap worth carrying into the real runtime, not just this POC.
- This board doesn't reset when a browser opens the WebSerial port (no auto-reset circuit wired the way `esptool`-flashable boards typically are) — a browser-triggered best-effort reset (`port.setSignals()`, the same RTS trick `esptool` uses) was added alongside the physical-reset fallback, explicitly documented as not working on all boards, since it depends entirely on USB-serial bridge wiring that varies.
- A client/device timeout mismatch (browser gave up waiting for a response before the device's own internal timeout would have) made a possibly-fine deploy look like a hard failure; fixed by keeping the client's wait comfortably longer than the device's worst case rather than shorter.
- The one genuine bug, not just a timing/UX gap: reading a specific byte count from `sys.stdin` (`read(n)`/`readexactly(n)`) turned out to hang this port's event loop outright — confirmed via checkpoint logging that it wasn't merely slow (the device's own internal timeout on that exact call never fired either), a real interpreter-level block, not a driver quirk `asyncio.wait_for` could route around. `readline()`, by contrast, had been reliable throughout. Fixed by removing `read(n)` from the protocol entirely: the bytecode now rides over as one base64-encoded text line, decoded with `binascii.a2b_base64`, verified byte-identical against real generated bytecode before ever touching hardware again. Worth flagging past this POC: whatever mechanism the real §13 protocol uses for binary payloads over serial needs to be checked against this same failure mode on whatever ports/boards v1 actually targets, not assumed safe because it works in the browser-side simulation.
- Two UX footguns, once the pipeline was actually working: `gpio_out`'s default pin (2) had no visible LED on this board (pins 12/13 do, matching POC-A's own wiring), which briefly looked like a logic bug rather than a picked-wrong-pin issue; and a leftover "inject now" preview button (carried over from POC-C, where it was a harmless canvas-only flash) was actively misleading in a build whose whole point is real deploys, since it looked like a live trigger but touched nothing — removed, since this POC's only real trigger is a full Deploy (inject's default `manual` repeat fires once, baked into the generated code, at the moment of deploy — there's no live re-fire round-trip in this protocol, by design per the out-of-scope list above).

None of these were foreseeable from the browser-only verification alone, which is exactly why §15.4 treats hardware runs as required rather than optional even after extensive off-device testing.
