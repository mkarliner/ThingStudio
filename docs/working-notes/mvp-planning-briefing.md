## Where things stand

All four pre-v1 POCs (§15) are done and their results are written into the
design doc and each `poc-*/README.md`:

- **POC-A** — live MicroPython/`uasyncio` runtime over WebSerial. Proven:
  ~99ms deploy-to-observable-behavior, 50/50 clean redeploys, no memory
  creep. Raw-source `exec()` is fast enough that bytecode isn't *forced* by
  latency (still an open call on other grounds — see below).
- **POC-B** — `mpy-cross` as WASM, compiled client-side. Proven: loads and
  compiles in-browser (and in plain Node), byte-identical output to a native
  build, ~1ms compile latency, no special hosting requirements.
- **POC-C** — Litegraph.js vs Drawflow canvas comparison. **§11's editor-library
  question is resolved: Litegraph.js.** It gave type-checked wiring, live
  value propagation, and multi-select natively; Drawflow needed all three
  hand-rolled and still can't do multi-select. Full comparison in
  `pocs/poc-c/README.md`.
- **POC-D** — the full pipeline merged: canvas → real compiler → real
  `.mpy` bytecode → real WebSerial deploy → runs on real ESP32-C3 hardware,
  confirmed working. Getting there surfaced real hardware-only bugs (see
  "Hard-won constraints" below) — worth reading `pocs/poc-d/README.md`'s "What
  broke and how it was fixed" before designing v1's protocol/runtime.

Nothing resembling a real v1 repo exists yet — only the throwaway `pocs/poc-a/`
through `pocs/poc-d/` folders plus the design doc. This is greenfield.

## Task 1: prioritize the MVP feature list

§10 has a rough, unprioritized v1 sketch (ESP32-C3 only, USB serial, a node
set, full-flow redeploy, live values, persistence). §15.5's out-of-scope
list is effectively "everything POC-D proved the pipeline for but didn't
build for real": the actual §6 compiler (general, not hardcoded to one
flow shape), the real `msg` envelope/type system, §13's real (CBOR-framed,
versioned) wire protocol, persistence, fault isolation, live value
streaming. That's the honest gap between "pipeline proven" and "v1 done" —
useful as a starting checklist to prioritize against, not a finished list.

Open questions in §11 that MVP scoping should either resolve or explicitly
defer, since each has real scope implications:

- MicroPython vs CircuitPython base port — never actually spiked.
- Human-readable Python vs compact intermediate form for generated code.
- Function node sandboxing (current lean: no, per §9's trust-perimeter argument).
- How node definitions are versioned/distributed between editor and device.
- Whether a no-hardware simulation mode is worth building.
- Runtime image update mechanism (OTA vs USB-only) — only the
  major-version-wipe *policy* is decided, not the mechanics.

## Task 2: code structure and conventions

§14 already calls the repo-structure question: single monorepo (editor,
device runtime glue, node library together), Apache-2.0. That's a real
decision, not yet executed — there's no repo skeleton yet.

Conventions established across the POCs, worth deciding explicitly whether
each carries into real v1 code rather than assuming yes by default:

- **Vendoring discipline**: `npm pack --ignore-scripts`, hash-verify against
  the registry's published `dist.shasum` before copying a file in, no
  runtime npm dependency, no build step, plain `<script src>`. Fine for
  throwaway POCs; a real editor app will likely want proper bundler/npm
  tooling instead — don't carry the "no build step" habit over by default,
  decide it.
- **Each POC is fully self-contained** (its own copy of vendored libs, no
  sharing between `poc-*/` folders) — deliberate for throwaway independence.
  Real v1 should have one shared dependency set, not this.
- **README per component**: scope, running instructions, a dated Results
  section appended once verified. Worth continuing for real v1 modules.
- **Verify off-device first, against real artifacts, before hardware**:
  headless Node.js exercising the actual library code (Litegraph core,
  mpy-cross WASM), real generated bytecode fed through real decode calls,
  adversarial/chunked input testing for wire protocols. Cheap, caught real
  bugs before hardware every time it was done.
- **Hardware is still authoritative** — POC-D's off-device verification was
  thorough and still missed 5 real issues only a real board surfaced (old
  harness silently dropping frames, no auto-reset circuit on this board, a
  client/device timeout mismatch, and the big one: `sreader.readexactly(n)`
  hangs this port's event loop outright, non-yielding, which
  `asyncio.wait_for` couldn't even preempt — fixed by routing the binary
  payload through `readline()` instead as a single base64 line). Whatever
  v1's real transport does with binary payloads needs the same hardware
  check early, not assumed safe from browser-side testing.
- **Design doc convention**: resolved open questions get struck through
  in place with a bolded "resolved \<date\> per §X" note rather than
  deleted, preserving the reasoning trail. Results sections are dated and
  appended after each POC's Success Criteria, not written as a separate doc.

## Hard-won constraints worth designing around from day one

- The transport/listener task needs the same fault-isolation treatment as
  deployed flow tasks, for a different reason: it can't fall back to a REPL
  while it owns the wire (§9's `kbd_intr` disable), so it must never be
  allowed to die from a bad exchange. This is now in §5.
- Don't assume a specific-byte-count read from a serial stream is safe on
  arbitrary MicroPython ports — verify per-port before committing v1's
  protocol to it.
