# Suspected: `mqtt_publish`/`mqtt_subscribe` boot-time race can silently drop a message

Found while investigating a real silent-failure hardware test, 2026-09-02: Mike's `basicmqtt.flow.json` (inject "manual" --> mqtt_publish; mqtt_subscribe --> debug, same broker/wifi config, qos 0, retain false) produced no debug output on real hardware, no error either.

Two contributing factors identified, not yet isolated from each other by a targeted test:

1. **`inject`'s click-fire is missing** (`inject-click-fire-missing.md`) -- "manual" actually fires once, automatically, at flow boot. If Mike was clicking the node expecting a live trigger, nothing was wired to respond regardless of the point below.
2. **No ordering guarantee between "subscription confirmed" and "publish allowed" when both share one client, at boot.** `mqtt-shared.ts`'s `mqttEnsureConnectedSnippet` only serializes the shared *connect* step (confirmed correct and tested -- `mvp-validation-plan.md`'s 2026-08-14 addendum, "two chains racing to connect the same client only actually connect once"). Once connected, `mqtt_publish`'s sink function proceeds straight to `await client.publish(...)` with no further yield forced before it; `mqtt_subscribe`'s source loop proceeds to `await client.subscribe(...)` independently. Both go through the vendored `mqtt_as`'s own internal `self.lock` (`__init__.py`'s `publish()`/`_usub()`), which serializes the two writes but does not guarantee which one wins the race to actually reach the broker -- and with qos 0 + retain false, if the PUBLISH packet arrives before the SUBSCRIBE does, the message is gone for good; `mqtt_subscribe`'s `await client.queue.__anext__()` then blocks forever, silently, with nothing to report.

This exact scenario was never covered by the existing off-device test suite -- `mvp-validation-plan.md`'s own addendum explicitly tested double-connect dedup only ("two chains racing to *connect*"), against a pymock broker that doesn't model real packet-arrival ordering at all. Not confirmed as THE cause of the 2026-09-02 silent failure (factor 1 alone is already sufficient to explain zero output), but a real, distinct gap either way -- worth a dedicated test once inject's click-fire exists to actually isolate it: fire publish well after confirming subscribe is up (should always work), and separately, a stress test firing them concurrently many times (to see how often the race actually loses in practice on real hardware/broker).
