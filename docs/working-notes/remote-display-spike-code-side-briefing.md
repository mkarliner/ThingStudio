Status: handoff, 2026-11-06. Continues `remote-display-spike-briefing.md` (the hardware session's own input).

## What landed (all on the branch)

- **`ts_http_server.py`** — the server is a general facility (Mike, 2026-11-06): added `mount()` for three
  route shapes (queued / static / WebSocket), the RFC 6455 subset in a `WebSocket` class, capped POST-body
  reading, per-route pre-checks for the socket gate. `http_in`'s own codegen is untouched; its routes work
  exactly as before; static and WS routes mount alongside.
- **`ts_remote`** (`device-runtime/src/vendor/thingstudio_remote/ts_remote/`, DEPENDENCIES entry): the whole
  board side — `Remote`, login over `TSAUTH1`, the WebSocket session, screen/values bridge from a real
  `RemoteSurface`, signed input frames, the deadman link policy, take-over. Page data (`page_data.py`,
  gzipped 9.7 KB) generated by `tools/build_remote_page.py` from `page/remote.html`.
- **`page/remote.html`** — flexbox mirror of `layout.ts`'s vocabulary, every built-in widget kind as data,
  unknown kinds as labelled placeholders, number/text fields + a settings form, a `ctl` slider at ~20 Hz,
  login, reconnect, take-over and link banners. Hand-written SHA-256/HMAC verified against Node's crypto.
- **`gui.py`** — one new method, `GUI.button_press(surface, wid, phase)`: a remote tap by id, same rules as
  `tap()`.
- **`test-flows/remote-display-spike.py`** — the hand-written spike flow (compiles through real mpy-cross);
  its walkthrough is the new section in `test-flows/README.md`.
- **SPEC** `interfaces/remote-display/SPEC.md` (draft) + `vectors/exchanges.json` — written from what the
  code sends; the runner note points at the two unix-port test files and the page-crypto test.
- **Version bump** — runtime/editor 15.0.0 → 15.1.0: additive libraries and server capability, no
  codegen/message change (minor).
- **Security policy** — the phone page becomes a zone/code source with its own section (§3.8, spike),
  `Check this first` gains the row. Package widget faces in the page stay in "not yet built".
- **Supporting**: `dep_compile.mjs` mkdir fix for nested package board files; learnings file
  (`learnings/remote-display-spike.md`, 6 entries); scoping note gained "where the spike stands in code".

## Known gaps / open threads for the hardware session

1. Everything in the checkpoint table (`remote-display-spike-results.md`): heap, latency, AP route
   (incl. Pico W STA+AP quirks and captive-portal DNS — **13 is unimplemented**, needs a UDP responder in
   `ts_http_server`-land; decide on hardware), discovery (`.local` behaviour; QR — ask Mike about an
   in-house encoder vs a dependency).
2. The page's `?t=` token in the URL is a recorded gap (security-policy §3.8), not a blocker for the spike.
3. `mount()` on an existing shared server after a `runtime.shared` factory built it with another owner's
   routes works (mount appends), but two flows each *constructing* the same port with different tables is
   still unhandled — fine for the spike's single-flow shape; the production `web_server` config node owns
   the merge. Note this in the results when the second-server case shows up.
4. The spike flow hand-writes what codegen would emit; nothing editor-side understands `ts_remote` yet
   (deliberately). The editor config node + descriptor is the first production work item if the spike says
   MVP.
5. `runtime.spawn` tasks of a session are *not* in `runtime._tasks`'s redeploys? They are — spawned via
   `runtime.spawn`, so a redeploy cancels them; verify on hardware with a redeploy while a phone is
   connected (the socket dies, the page reconnects — that is the pass condition).
