    Debugging & troubleshooting

    What the console and compiled source show, and what to do when a board or deploy fails.

    Console and compiled source

    The console shows what the board and Thingstudio report: deploy results, node errors, and what debug nodes and print() send. Clear empties it.

    Its Show menu sets how much it shows:

    • Normal: your flow's output, warnings, errors, and the results of what you do, such as a deploy.
    • Info: adds routine reports: board detected, versions, memory, libraries sent, network status.
    • Debug: adds raw protocol messages and the board's boot output.

    Hidden lines are kept, so choosing Info or Debug later shows what was already logged.

    The Compiled source panel shows the MicroPython your flow compiles to.

    The editor's version is next to its name in the toolbar, and in Help → About Thingstudio. A + after it means you built it from uncommitted changes. Include the versions when you report a problem.

    Memory

    With Show set to Info, a [memory] line after each connect and deploy shows the board's free RAM. On an ESP32 it also shows the ESP-IDF heap and its largest free block. WiFi, MQTT and TLS use the ESP-IDF heap, not MicroPython's. If WiFi won't join while MicroPython has plenty free, a low ESP-IDF figure is the likely cause. The FAQ explains where an ESP32's memory goes.

    Commands and the Python prompt

    The command box under the console runs Python on the board. Type a line and press Enter; the result appears in the console. The up and down arrows bring back earlier commands.

    gc.mem_free()
import machine; machine.Pin(15).value()
os.listdir()

    Commands run alongside your flow, and variables you set stay for the next command. A command that takes time, such as a sleep or a loop, holds up the flow until it finishes.

    The stored application values are available as settings:

    settings.namespaces()      # each flow's name and how many values it holds
settings.clear()           # clear the current flow's values
settings.clear_all()       # clear every flow's values

    Use these if a saved value is wrong, or a flow you no longer deploy left values behind. Clearing takes effect immediately; the next read returns the default. Tools → Clear device settings… does the same from the editor: choose the current flow, or every flow.

    For MicroPython's own >>> prompt, click Stop flow & open prompt. The flow and the runtime stop; nothing is deleted. What you type in the box now goes to that prompt, and Deploy is off. Click Restart Thingstudio to start the runtime and the saved flow again.

    To use the prompt from another program, such as Thonny or mpremote, click Connected · Disconnect first.

    Watching a board start up

    To see a board's own startup messages, connect with mpremote connect PORT and no further command, or a serial monitor that doesn't send Ctrl-C when it opens. A working runtime prints LISTENER_BOOTING, then LISTENER_READY.

    mpremote repl and Thonny's Shell interrupt the board as they connect, which looks like a board that never starts. Close them before connecting from Thingstudio: only one program can use the port at a time.

    Board won't connect

    When Connect, Tools → Check status or Tools → Install runtime… gets no proper reply, the console says what the board sent instead, and what to do:

    Console says What to do
    Nothing came back Usually no MicroPython. Install MicroPython. If it's there, press reset, then Tools → Check status.
    MicroPython but no Thingstudio runtime Tools → Install runtime….
    MicroPython replied but didn't enter install mode Press reset and install again.
    Board is in its bootloader An ESP32 in download mode. Press reset, not BOOT. If it repeats, install MicroPython.
    Board runs CircuitPython, or replied but not as MicroPython Install MicroPython.
    Runtime still starting Wait, then Tools → Check status.
    Install stalled Replug the board, click ⟳, and try again. If it repeats, restart Thingstudio.

    If the port itself won't open, the console says why:

    Console says What to do
    port in use Close other serial monitors, IDEs, or editor tabs using the board.
    port access refused Replug the board and check port permissions. On Linux, check you're in the dialout group.
    board gone from that port Check the cable, click ⟳, and connect again.

    The raw error stays in the message, in brackets. Include it if you report a problem.

    Install firmware… fails or lists nothing

    Tools → Install firmware… writes MicroPython onto a board in its bootloader. Each refusal names the step:

    What the dialog says What to do
    (no serial ports found), or the board's port is missing Put the board in download mode — hold BOOT, tap RESET, release BOOT — then click ⟳.
    (no mounted drives found), or the drive you want isn't listed Hold BOOTSEL while plugging the board in, then click ⟳. If it's mounted somewhere the list doesn't look, type the path in the box under the list — on macOS a Pico shows up as /Volumes/RPI-RP2.
    A port named /dev/ttyS0, /dev/ttyS1… Those are the computer's own serial ports, not the board. USB ports are listed above them, labelled with their path and the adapter's name (/dev/ttyUSB0 -- CH340).
    … is not a .uf2 A mounted drive takes the .uf2 build, not a .bin. Download the right one from micropython.org/download.
    … is not the image this board expects The file isn't the image that board's entry pins. Pick the board's own image, or choose a different board entry.
    The board doesn't start after flashing a file with no board The Address was wrong for the chip: 0x1000 for an ESP32 or ESP32-S2, 0 for an ESP32-S3, C3, C6 or ESP8266. Flash again with the right one; the board is recoverable.
    esptool is not installed on this machine The backend's Python has no esptool: pip install esptool, then restart Thingstudio.
    esptool exited N at … on PORT The write stopped. Check the cable, put the board in download mode again, and retry. A board with a separate USB-serial chip may need the slower write: clear its baud in the board file, or use the terminal route in Install MicroPython.
    the flash did not finish within … The tool stopped answering. Unplug and replug the board, then flash again.

    A flash that finishes but leaves the board silent usually means the image is stock MicroPython: connect it, then Tools → Install runtime….

    Deploy is grayed out

    Compile → Deploy is grayed out when:

    • the editor isn't connected to a board;
    • the flow on the board is the one on the canvas, deployed and unchanged since;
    • the flow is stopped at the Python prompt (click Restart Thingstudio);
    • the board is restarting.

    Module missing on the board

    A deploy can fail with ImportError: no module named '...': the flow needs a module the board's MicroPython doesn't have. The board keeps running its previous flow.

    The usual cause is networking. MQTT, UDP, HTTP and WiFi nodes need the network and socket modules, which only boards with WiFi or Ethernet have. A Raspberry Pi Pico has neither; a Pico W does. If the board reports no WiFi, the console warns you before the deploy.

    Other modules differ between ports and builds. If the import is in your own function node, check the module exists for your board in the MicroPython docs. A board that should have it may need a different MicroPython build.

    Thingstudio's own libraries, such as the MQTT client and display drivers, are sent by Deploy. See Libraries.

    MemoryError or a library that won't load

    A board can be short of memory while its [memory] line still shows free RAM. The free RAM is in pieces, and a flow or a library needs one piece big enough to fit. This is common on boards with little RAM, most of all on an ESP32 without PSRAM once a display flow has run.

    When a deploy fails this way, work through these in order:

    1. Tools → Remove flow… — so nothing is resumed at start-up.
    2. Power cycle the board — unplug its USB cable and plug it back in, or Tools → Reset board (hard).
    3. Deploy again.

    Removing the flow alone does not help: the running flow keeps its memory until the chip restarts. A soft restart does not help either — it restarts the interpreter over the same heap regions and gives no chip memory back. Only a power cycle gives the board a clean heap, which is why it is the step above.

    If it still fails after the power cycle, the flow may be too big for this board. That is a limit of the board, not a fault in the flow. Three things can still work:

    • Make the flow smaller. Fewer pages in the GUI, fewer libraries imported, a smaller frame. The gui screen node sends a frame in strips for this reason; a function node that builds a whole frame at once still needs one big block.
    • Use a board with more memory. Boards with PSRAM have room for flows a board without it cannot start.
    • Run a firmware image with the libraries built in. On a classic ESP32 there is a ready-made one: Custom firmware for classic ESP32. On other boards the same technique works — freeze the runtime and the flow libraries into MicroPython — if you build your own.

    If none of those is possible, the flow does not fit that board. Nothing in the editor can make room that the board does not have.

    Deploy does not try to fix this for you: it reports the failure and stops, because freeing or restarting on your behalf would leave the board in a state you didn't choose. When the board looks short of memory before a deploy starts, the console says so in one line (only 19 KB free on the board, this flow is 10 KB -- it may not fit) and deploys anyway. That figure is total free memory, not the largest free block, so it is a hint rather than a verdict.

    WiFi Internal State Error on deploy

    On an ESP32, deploying a flow with MQTT nodes can fail with "Wifi Internal State Error". The board is still reconnecting to the network the previous flow used, and refuses a new connection until that finishes. The MQTT nodes retry up to three times. If it still fails, deploy again.

    Deploy resends a piece, or fails part-way

    Deploy sends the flow, and each library it uses, in pieces, and waits for the board to confirm each one. Over a USB-serial chip such as the CYD's, a piece can arrive damaged or its confirmation can get lost. The console then shows resending (1/2), and Deploy carries on. That is normal now and then.

    If a piece still fails after three tries, Deploy stops and says so, and the flow on the board is unchanged. Deploy again. If it keeps happening, try another USB cable or port, close anything else using the serial port, or connect over WiFi.

    The console shows [protocol] illegal or PROTOCOL_ILLEGAL

    The editor and the board follow a fixed set of moves when they talk. A line starting [protocol] illegal (from the editor) or PROTOCOL_ILLEGAL (from the board) means one of them made a move that isn't in that set. It is a bug in Thingstudio, not something you did. Deploy carries on or fails cleanly either way. Please report it with the console lines around it.

    Reading a node error

    When a node fails on the board, the console shows a [NODE_ERROR] line naming the node and the error, and the node is highlighted on the canvas. Network nodes (udp send, udp receive, http request, mqtt publish, mqtt subscribe) also name the operation and the host and port. A network node error without them is worth reporting.

    I2C device not answering

    A sensor node's status dot shows disconnected, with "no reply at 0x76", when nothing answers at its address. Scan the bus to see what is there. Type these two lines in the command box, one at a time, with your bus and pins:

    i2c = machine.I2C(0, scl=machine.Pin(5), sda=machine.Pin(4))
[hex(a) for a in i2c.scan()]

    An i2c device node set to scan does the same from a flow.

    An empty list means nothing answered. Check these, in order:

    • The pin numbers. On a Pico, GP4 and GP5 are physical pins 6 and 7.
    • SDA and SCL swapped.
    • Power (3.3 V) and ground to the device.
    • Solder joints on the header pins.

    An address different from the node's means the address is wrong, not the wiring.

    A toggle button goes back

    A gui toggle with its input wired shows the state you asked for until the input confirms it. If nothing arrives within wait for confirmation (5 s by default), it goes back to its last state, shows a cross for a moment, and the console shows NODE_ERROR ... NoConfirmation: no confirmation within 5 s.

    Check these, in order:

    • The device is reachable and the command reached it. Watch the command topic with a debug node.
    • The input is wired to the device's state topic, not the command topic.
    • The state is sent in a form the toggle matches. A toggle set to true and false ignores ON and OFF: set its value type to text.

    Native code (Tools → Native code)

    The gs4, gs2 and mono frame formats of display spi compile part of their code to native machine code, which needs the right architecture for the board's chip.

    Tools → Native code defaults to Arch: Auto, which uses the processor of the board in the Board menu. If Deploy fails with an architecture or native-module error, pick your board's chip from the list and deploy again.

    Restarting the board

    A board can run short of memory after several deploys, or after a flow that uses a lot of it, such as a display. The console suggests a restart when a deploy fails with MemoryError, the board restarts while starting a flow, or an ESP32 has too little memory left for WiFi.

    The Tools menu has two restarts:

    • Tools → Restart board (soft) restarts MicroPython. The saved flow starts again with a clean interpreter: the flow's own objects are gone, but the heap regions are the same ones and memory MicroPython took from the chip is not returned. USB stays connected.
    • Tools → Reset board (hard) resets the whole chip, like its reset button, and frees all memory. A board with native USB (Pico, ESP32-S2, S3 and C3) disconnects; click Connect when it's back.

    A soft restart is enough to clear a flow's own leftovers, such as a big buffer a faulty node left behind. It is not enough for a board that cannot fit a deploy: nothing short of a full power cycle gives the memory back in one piece, so that case is Remove flow…, power cycle, deploy (above). When an ESP32 is short of memory for WiFi, only the hard reset helps either. The console says which to use. Deploy is off until the board is back, which can take several seconds.

    Board stuck restarting

    A flow that crashes the board as it starts would crash it on every restart. If the saved flow doesn't stay up for 10 seconds on three restarts in a row, the board starts without it, and the console shows [safe mode]. Fix the flow and deploy it again, or remove it.

    Tools → Remove flow… deletes the saved flow from the board, for any flow that stops the board answering:

    1. Select the board's port and choose Tools → Remove flow….
    2. If the console asks, press the board's reset button. Thingstudio keeps trying for a minute.
    3. When it's done, click Connect.

    The board then starts with the runtime only, as after a fresh install. The flow on your canvas isn't affected.
