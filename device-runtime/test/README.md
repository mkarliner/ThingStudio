# device-runtime/test

Headless MicroPython unix-port tests (design doc §15 convention, formalized in `docs/working-notes/validation/mvp-validation-plan.md`). No longer a placeholder — this environment did not ship a MicroPython build, but building one from source is straightforward and is now the actual verification path fault-isolation-briefing.md's work was run against. Not a substitute for the real hardware pass (see `../../docs/working-notes/validation/mvp-validation-plan.md`'s "Fault isolation" section) — this is real `uasyncio` scheduling and real generated bytecode, but not real silicon, real timing, or the witness rig's independent liveness check.

## Building the tools (once per machine)

Two separate binaries, both built from the **same MicroPython commit** so bytecode versions match — a `.mpy` compiled by a different commit's `mpy-cross` is not guaranteed loadable by a mismatched `micropython` build.

```sh
git clone --depth 1 https://github.com/micropython/micropython.git mpy-src
cd mpy-src
make -C mpy-cross
cd ports/unix
make submodules
make
```

This produces:
- `mpy-src/mpy-cross/build/mpy-cross` — the cross-compiler (same tool `pocs/poc-b` and `mpy-cross-wasm/` wrap for the browser; this is a native build for local/test use, not the WASM one).
- `mpy-src/ports/unix/build-standard/micropython` — the headless interpreter these tests run against.

Neither binary is vendored into this repo (they're machine-specific native builds, not source) — build once locally, keep the paths, reuse across sessions. `import uasyncio` works out of the box in this build (aliased to the port's bundled `asyncio`); no extra `mip`/package install needed for anything these tests use (`uasyncio`, `binascii`, `struct`, `gc`, `sys`).

## Running the tests

Each `test_*.py` file is self-contained and runnable directly:

```sh
MICROPYTHON=/path/to/mpy-src/ports/unix/build-standard/micropython
$MICROPYTHON test_cbor.py
$MICROPYTHON test_framing.py
$MICROPYTHON test_protocol.py
$MICROPYTHON test_runtime.py
$MICROPYTHON test_board_settings.py   # WiFi transport: hostname, password key, HMAC, challenge/verify
```

Each prints a `PASS`/`FAIL` line per test (via `minitest.py`, a hand-rolled runner — see its own header comment for why: this MicroPython build has no `unittest` module) and exits non-zero if anything failed.

`test_listener_integration.py` is different: it's a **CPython3** script (needs `subprocess`/`threading`, which the point above doesn't have in this minimal build), driving a real `micropython listener.py` subprocess over real stdin/stdout pipes -- the closest thing to the real WebSerial hardware pass achievable without a board. It needs both binaries above, plus `mpy-cross` to compile small test flows on the fly:

```sh
MICROPYTHON_BIN=/path/to/micropython \
MPY_CROSS_BIN=/path/to/mpy-cross \
python3 test_listener_integration.py
```

Skips (exit 0, prints `SKIP: ...`) rather than failing if either env var isn't set — same "honest about what isn't covered here" convention as every prior hardware-adjacent piece of this project, since not every environment running the rest of this suite will have both binaries built.

## What's covered here vs. what still needs real hardware

Covered, against real MicroPython (not a mock): CBOR encode/decode including adversarial/garbage input (`test_cbor.py`), frame reassembly including the 50-malformed-frame soak case (`test_framing.py`), message round-trip and shape validation (`test_protocol.py`), the per-task fault-isolation boundary under real `uasyncio` scheduling — including "the rest of the flow keeps running" (`test_runtime.py`) — and, end-to-end over a real byte-stream pipe with real `mpy-cross`-compiled bytecode, `HELLO` on boot, `DEPLOY`/`DEPLOY_ACK`, `NODE_ERROR` reported with the correct node ID, and listener survival through 50 malformed frames in a row (`test_listener_integration.py`).

Still needs the real witness+DUT rig (`../../test/hil/`), per the validation plan: real silicon timing, the witness board's independent `HEARTBEAT_WATCH` (this test suite can't observe the DUT's heartbeat GPIO pin at all), and confirming the base64/`readline()` transport choice actually holds on this port's real hardware (`fault-isolation-briefing.md`'s own "Verify per-port" note) rather than just the unix-port's stdin/stdout pipes.
